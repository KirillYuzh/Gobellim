## Что трогать нельзя

Перечисляю, чтобы не переписали при рефакторинге.

- Порядок Gate в `gate.go:23-48`. Tenant → target → grounding → Authorizer → Validate →
  потолок доступа. Grounding до ACL, потому что выдуманный моделью id не должен
  доходить до ACL приложения. Это правильная и редкая мысль.
- `execute` идёт только из `decide`. Один вход, нет второго пути к handler. Плюс
  `internal/importrules` как build-time защита графа пакетов.
- `PendingAction.Proof`: HMAC по всем полям карточки, включая `Reason` и `Provenance`.
  Подписать карточку целиком, а не только аргументы, - правильный выбор, потому что
  апрувер решает по карточке.
- Claim до исполнения (`task.go:409-415`). Потеря одобрения при краше лучше двойного
  списания. Это осознанный трейд, и он записан комментарием, а не забыт.
- `decodeStrict` + `scanJSON`. Три прохода по недоверенному JSON выглядят избыточно,
  пока не посмотришь на `DisallowUnknownFields`, дубли ключей, глубину и `null`.
- `Effect`/`Access` без разрешающего нулевого значения. Забыть объявить эффект нельзя.

# BLOCKER

## BLOCKER-1. Документация описывает другой API, включая инвариант безопасности

**Что не так.** Ни один из двух сниппетов, которые новый пользователь копирует первыми,
не компилируется.

`README.md:184-195`:

```go
refund := gobellim.Tool[RefundArgs, RefundResult]{
    Name:   "orders.refund",
    Effect: gobellim.Write,       // поля Effect у Tool нет
    Resource: func(...) ... ,     // поля Resource у Tool нет
}
```

Реальные поля: `Access` и `Target` (`tool.go:21,28`).

`README.md:331-373` (раздел Human approval) целиком не существует в коде:
`flow.NewSealer`, `flow.WithSealer`, `wf.ApprovePending`, `Suspension.Token`,
`wf.Resume(ctx, approver, token, decision)`. Фактический API: `flow.New`, `Step`,
`Approve(id, cfg)`, `Resume(ctx, approver, susp, state, decision)`. В `flow/flow.go:80`
прямым текстом написано `There is no sealed bearer token`, а README на строке 26
заявляет, что "sealed continuations" реализованы.

Дальше хуже, чем косметика. `README.md:244-248` и `DESIGN.md:277-303` описывают четыре
уровня `Integrity`, включая `Validated`. В `labels.go:12-20` их три, `Validated` нет.
`DESIGN.md:303` и `AGENTS.md` утверждают: "единственное повышение в ядре - `Tool.Validate`
вернул nil на handle-аргументе". В коде `Tool.validate` (`tool.go:156-165`) возвращает
только ошибку и ничего не повышает, а `labels()` (`schema.go:640-653`) учитывает лишь
`sensitivity`. Тесты репозитория прямо утверждают противоположное документации:
`TestUntrustedHandleWithValidatorStillEscalates` и `TestGroundedHandleWithoutValidatorEscalates`.

**Почему это важно.** Пользователь читает "это единственный путь от ввода модели к
непосредственному Write: handle + Validate", строит на этом доступ к возвратам денег и
получает систему, которая ведёт себя иначе. Настоящий путь повышения доверия в коде
другой: `source=principal` или `source=application` на поле **входа** даёт метку
`Trusted`, из неё рождается handle, и только такой handle разрешает Write без человека.
Это нигде не описано как механизм повышения. Документация врёт в сторону, которая
выглядит безопаснее, чем код.

**Как исправить.**

1. Переписать Quickstart и раздел Human approval под фактический API.
2. Убрать `Validated` из README и DESIGN, описать реальный путь: `source=...` → `Trusted`
   label → handle → Write разрешён.
3. Пометить `DESIGN.md §8.5` (AES-GCM continuation) как "не реализовано" либо удалить.
4. Синхронизировать `AGENTS.md` в том же коммите: сейчас он содержит `Effect`,
   `EffectUnknown`, `Resource` и несуществующее повышение через `Validate`.
5. Добавить doc-тест: файл `example_test.go` с `// Output:` на Quickstart. Тогда дрейф
   документов падает в CI, а не приходит баг-репортом через месяц.

**Чем лучше.** Обещание "инварианты проверяемы" становится правдой, и цена поддержки
падает до одной команды `go test`.

## BLOCKER-2. `source=application` на аргументе инструмента принимается и молча игнорируется

**Что не так.** `nodeForType` (`schema.go:292-306`) разрешает тег `source` на любом
string-поле, включая аргументы инструмента. `labels()` (`schema.go:640-653`) применяет
только `sensitivity`, а базовая метка в `Tool.prepare` (`tool.go:123`) всегда `Derived`.
Прогон:

```
type Args struct {
    OrderID string `gobellim:"required,ground"`
    Note    string `gobellim:"source=application"`   // <-- "доверенный" аргумент
}
...
call orders.refund: escalate [write-untrusted] "write arguments are model-derived"
provenance: Note <- model (derived)
```

**Почему это важно.** Это fail-silent на теге безопасности. Разработчик объявил значение
принадлежащим приложению, `NewTask` это принял без ошибки, и тег не сделал ничего.
Разница между "тег отсутствует" и "тег есть, но не работает" стоит дорого: первый случай
заставляет читать документацию, второй создаёт ложную уверенность. Тот же дефект у
`gobellim:"ground"` на поле входа (прогон: `Ticket string \`gobellim:"ground"\``проходит`NewTask` и ни на что не влияет).

**Как исправить.** Передавать в `nodeForType` контекст схемы (вход задачи либо аргументы
инструмента) и отклонять `source`/`ground` в схеме аргументов с `ErrInvalidConfig`.
Тест: `NewTask` с `Tool[Args]`, где у поля `source=application`, возвращает ошибку.

**Чем лучше.** Ошибка конфигурации видна на старте, где её и хотят видеть, вместо
необъяснимого `escalate` в проде.

## BLOCKER-3. Карточка одобрения отдаёт сырые секреты и не сообщает, что это секреты

**Что не так.** `gate.go:97` кладёт в карточку `json.Marshal(c.args)`, то есть
**разрезолвленные** значения. `Provenance` (`approval.go:13-17`) содержит `Arg`, `Source`,
`Integrity` и не содержит `Sensitivity`. Прогон:

```
CARD args: {"OrderID":"A-1042","Note":"model wrote this","Cents":100}
provenance: OrderID <- input:OrderID (untrusted)
```

`A-1042` - то самое значение, которое модель никогда не видела, потому что поле помечено
`sensitivity=secret`.

**Почему это важно.** Библиотека обещает "сырые секреты не попадают в промпт", а затем
кладёт секрет в JSON, который приложение сохраняет в БД, отдаёт в UI апрувера и, с
вероятностью близкой к единице, в лог. DESIGN §8.4 говорит "сервис обязан применить
approver ACL", но ACL отвечает на вопрос "можно ли этому человеку видеть объект", а не
"какие поля нужно замаскировать". Метка, которая нужна для второго вопроса, до карточки
не доезжает.

**Как исправить.**

1. Добавить `Sensitivity` в `Provenance`. Пять строк, и UI наконец может решить, что
   маскировать.
2. Дать `ApprovalCard` маскированную копию аргументов (secret → `<h1>`, pii по регуляркам)
   рядом с сырыми, и сделать сырые opt-in через `Engine.CardOptions{ShowSecrets: true}`.
3. Дефолт - маскированная карточка. Апруверу для решения почти всегда достаточно
   "заказ <h1>, 4900 копеек", а не самого номера.

**Чем лучше.** Карточка остаётся полезной, но перестаёт быть вторым каналом утечки.

## BLOCKER-4. Handle-плейсхолдеры утекают в пользовательский вывод

**Что не так.** `decodeOutput` (`task.go:577-597`) проверяет размер, форму JSON и схему
и ничего не делает со строками. Прогон:

```
OUTPUT: "Заказ <h1> возвращён, чек на <h2>"
```

`<h1>` - настоящий handle заказа, `<h2>` модель выдумала.

**Почему это важно.** Первый же реальный ответ клиенту будет содержать `<h1>` вместо
номера заказа. Это не проблема безопасности, это проблема внедрения: продукт выглядит
сломанным в самом заметном месте. И одновременно это упущенная возможность: если
резолвить handle в выходе, модель сможет возвращать пользователю настоящие значения,
которые сама не видела.

**Как исправить.** Выбрать одну семантику и записать её в контракт.

- Дешёвый и fail-closed вариант: в `decodeOutput` заменять любой `<hN>`, которого нет в
  `handleSet`, на пустую строку, а существующие резолвить. Плюс правило `output-handle`
  в аудит, чтобы видеть частоту.
- Точный вариант: тег `resolve` на полях `Out`, резолв только там, где приложение
  осознанно разрешило.

**Чем лучше.** Утверждение "handle не покидает runtime" становится проверяемым, и в
`Out` не может появиться значение, которое модель не получала.

## BLOCKER-5. Два примитива одобрения, две конфигурации, и главный сценарий не проверен

**Что не так.**

`PendingAction` подписан HMAC по всей карточке (`approval.go:64-105`). `Suspension`
(`flow/flow.go:81-86`) содержит `Nonce`, `Card`, `ExpiresAt`, `Requester` и не подписан
ничем. Защита держится на том, что приложение хранит `Suspension` у себя; при этом
`Resume` берёт `requester` из самой структуры, то есть из объекта, который проходит через
HTTP и хранилище.

Конфигурация дублируется. `Engine` требует model, authorizer, audit, limits, claims, ttl,
key, clock (`engine.go:10-26`). `Flow` заново требует authorizer, audit, store, ttl,
walltime, clock (`flow/flow.go:96-105`), и `flow.Store` и `gobellim.ClaimStore` - один
интерфейс под двумя именами.

Главного сценария нет ни в примерах, ни в тестах:

```
grep -rn "ExecuteApproved\|PendingAction" flow/ examples/
→ flow/store.go:13 (комментарий), examples/06 (ExecuteApproved без flow),
  examples/01 (упоминание в тексте)
```

Ни одного теста, который проводит `PendingAction` через `Flow.Suspend`/`Resume` и
`ExecuteApproved`. Ни одного примера. README показывает эту связку вымышленным API.

**Почему это важно.** Пользователь, которому нужно "модель предлагает → менеджер
утверждает → возврат выполняется", обязан сложить Engine + Task + Tool + PendingAction +
Flow + Suspension + ApproveConfig + ApproverFrom, и половину этого пути ему показывают
неверно. Это не второстепенный сценарий, это причина, по которой библиотеку берут.

**Как исправить.**

1. Написать `examples/notebooks/07_task_flow_approval` и тест, который проходит полный
   круг: `task.Run` → `PendingAction` в состоянии → `flow.Suspend` → `flow.Resume` →
   `task.ExecuteApproved` → повторный `Resume` даёт `ErrReplay`.
2. Подписать `Suspension` тем же ключом (HMAC по полям, как `proofMessage`), либо убрать
   `Requester` из `Suspension` и передавать его в `Resume` отдельным аргументом. Первое
   лучше: тогда обе структуры одобрения имеют одинаковую модель угроз.
3. Если после шага 1 окажется, что Flow нужен одному сценарию из десяти, вернуться к
   разделу "Что удалить".

**Чем лучше.** Единственный путь к внешним эффектам получает тест, а не абзац в DESIGN.

# HIGH

## HIGH-1. `Resource.TenantID` по умолчанию подставляет tenant вызывающего

`gate.go:25-27` заполняет пустой `TenantID` из `p.Tenant`, и только потом сравнивает.
Значит проверка "объект принадлежит tenant" выполняется после подстановки и не может
провалиться. Прогон: `Target` вернул `{Type:"order", ID:a.OrderID}` без tenant, Gate
пропустил.

**Почему важно.** Самый сильный инвариант деградирует от забывчивости. `AGENTS.md`
предупреждает про деградацию ACL при отсутствии target, но про tenant молчит, хотя дыра
здесь шире: target есть, проверка формально прошла, объект может быть чужим.

**Fix.** Для всего, кроме `Compute`, требовать непустой `TenantID` либо в `Tool.check`,
либо в `check()` возвращать `RuleTargetUnbound`, если `Target` вернул пустой tenant.
Подстановку из principal оставить только для `Compute`.

## HIGH-2. `go.mod` требует Go 1.26 при фактическом минимуме 1.24

`go 1.26.0` в `go.mod`. Максимум, что реально используется, - `slog.DiscardHandler` в
`testkit.go:150` (Go 1.24). `context.WithoutCancel` и `max()` требуют 1.21.

**Почему важно.** Библиотека для внедрения в существующие сервисы. Требование обновить
тулчейн до последнего минора отсекает часть потребителей без выигрыша. Для библиотеки
"go get и всё" это самый дешёвый способ потерять первую интеграцию.

**Fix.** `go 1.24.0` и матрица CI 1.24/1.25/1.26.

## HIGH-3. Бенчмарк в репозитории падает, release workflow ссылается на пустоту

```
go test . -bench . → BenchmarkGateDecide
  bench_test.go:65: decision = {deny [target-unbound] action has no target}
```

Бенчмарк создаёт `Tool{Access: AccessRead}` без `Target`, то есть мимо `NewTask`, и
упирается в правило, добавленное позже. CI бенчмарки не запускает, поэтому поломку
никто не заметил.

`.github/workflows/release.yml` перебирает `mcp webfetch eval kittest cmd scripts
plugins/elasticsearch plugins/otel`. Из одиннадцати каталогов существуют два (`flow`,
`plugins/gigachat`). Первый тег упадёт на генерации SBOM.

**Fix.** Добавить `Target` в бенчмарк. Прогонять `go test -bench . -benchtime=1x` в CI.
Список каталогов в release заменить на фактический.

## HIGH-4. Мультиреплика ломается в рантайме, а не на старте

`engine.go:113-118`: без `WithApprovalKey` ключ случайный на процесс. Escalation на
реплике A, approve на B даёт `ErrApprovalDrift` ("pending action was not issued by this
engine"). `MemClaims` тоже per-process. Дефолт безопасен, но операционно неверен:
пользователь узнаёт о проблеме на первом же approval в проде.

**Fix.** Один `slog.Warn` в `New`, когда `Claims` или `ApprovalKey` не заданы явно:
"approvals are bound to this process; set WithApprovalKey and WithClaimStore for
multi-replica". Либо вернуть ошибку на комбинацию "ключ задан, store нет".

## HIGH-5. `MemClaims`: линейный обход под мьютексом на пути одобрения

`claims.go:38-70`: каждые 512 клеймов `forgetLocked` проходит по всей карте под мьютексом,
дефолтный лимит `1<<20`. При миллионе живых записей это миллион итераций с блокировкой,
останавливающей все остальные approvals процесса.

**Почему важно.** Дефолт используется в проде чаще, чем `store/sql`, потому что работает
без настройки. Ступенька появится в p99 в самый неудачный момент: при всплеске approvals.

**Fix.** Минимум: снизить `defaultMaxClaims` до 64k (за час процесс не накопит больше
при разумном TTL) и вынести sweep за пределы критической секции. Правильно: heap по
`expires_at` либо фоновая очистка по тикеру с явным владельцем горутины.

## HIGH-6. Контракт `Sink` не описывает ни конкурентность, ни блокирование

`audit.go:77-80` говорит "must not block the caller for long". `Engine.emit` вызывается
на goroutine вызывающего для каждого события: старт, каждый ответ модели, каждое решение
Gate, каждый tool. Это 5-7 вызовов на run.

**Почему важно.** Пользовательский sink с сетью превращает это в 5-7 сетевых вызовов в
latency запроса. `plugins/langfuse` в этом же репозитории как раз асинхронный и с очередью,
то есть автор понимал проблему, но контракт об этом не сообщает.

**Fix.** Зафиксировать в интерфейсе: "Emit must be safe for concurrent use and must not
perform I/O on the caller's goroutine; buffer and flush in your own goroutine". Это два
предложения, которые снимают целый класс интеграционных ошибок.

# MEDIUM

**M1. `Access` против `Effect`.** Значения `Read/Write/Send/Delete/Compute` описывают, что
инструмент делает с миром, то есть эффект. Слово `Access` в Go-мире означает права
доступа, а `AccessCompute` читается как "право на вычисление". Прежнее имя `Effect` было
точнее, и rename стоил разъезда всей документации. Если имя менять обратно дорого, хотя бы
не оставляйте `Effect` в DESIGN и AGENTS.

**M2. Два `Decision` и `Approve`, который одновременно константа и метод.**
`gobellim.Decision{Deny,Allow,Escalate}` и `flow.Decision{Approve,Reject}` означают разные
вещи под одним именем. `wf.Resume(ctx, approver, susp, state, flow.Approve)` читается так,
будто передают метод. Переименуйте в `flow.Choice` или `flow.Approval`, значения в
`flow.Approved` / `flow.Rejected`.

**M3. `sensitivity=secret` перегружен ролью "сделай значение ссылаемым".** README прямо
советует: "чтобы модель могла ссылаться на значение, пометьте поле `sensitivity=secret`".
Конфиденциальность и адресуемость - разные свойства. Разработчик пометит ИНН как secret
только чтобы модель могла его вернуть, и потеряет исходный смысл метки. Нужен отдельный
тег `handle` (или `ref`), а `sensitivity` оставить про раскрытие.

**M4. `ground` без значения привязан к совпадению имён.** `groundSource` (`schema.go:716-728`)
сравнивает `Sources[0].ID` с путём аргумента. Источником служит путь поля во входной
схеме, поэтому совпадение имён `OrderID` во входе и в аргументах - неявная конвенция.
Переименование поля входа ломает grounding только в рантайме, ответом Deny. Либо
требовать явный `ground=<input.path>`, либо проверять на `NewTask`, что объявленный
источник существует во входной схеме.

**M5. Panic не перехватывается, и об этом не написано.** `TestPanicIsAuditedAsFailure`
фиксирует поведение: паника проходит через `defer` библиотеки (событие `task.failed` с
`Error: "incomplete"`, потому что `err` остался nil) и уходит в вызывающий код. Решение
защитимое, но в "Guarantees" README об этом ни слова. Одна строка "your HTTP server must
recover; a panic in a tool handler is not converted to a Deny" экономит полдня отладки.

**M6. `TaskConfig.FourEyes` дублирует `flow.ApproveConfig.FourEyes` более слабой
гарантией.** В Task приложение само передаёт `approvedBy` и сравнение идёт по `UserID`
(`task.go:373`). В flow четыре глаза проверяются после `authz.Allowed` на апрувера. Два
одноимённых переключателя с разной силой - приглашение выбрать неправильный. Оставьте
один, в flow.

**M7. 2095 строк документации на 3254 строки кода, в двух языках, с тремя описаниями
порядка Gate.** `README.md`, `README.ru.md`, `DESIGN.md` (759 строк), `AGENTS.md`,
`docs/README.md`, плюс Next.js-сайт в `site/`. Дрейф уже произошёл во всех пяти файлах
одновременно. Дублирование гарантирует, что он произойдёт снова. Предложение: DESIGN
оставить спецификацией и сократить, README один (второй язык генерировать или не держать),
`docs/` заменить на godoc-примеры, которые компилируются.

**M8. Смешение языков в одном наборе документов.** README и AGENTS на английском, DESIGN
и docs на русском. Для библиотеки с внешними пользователями это выбор, который стоит
сделать явно, а не оставлять как есть.

# Обязательные вопросы

1. **Какая задача решается?** Один use-case с LLM внутри существующего Go-сервиса, где
   модель предлагает действия, а решение принимает детерминированный Gate. Ответ влезает
   в строку, это хороший знак.
2. **Минимальная версия?** Engine + Task + Tool + Gate + audit. Всё остальное (Flow,
   langfuse, gigachat, store/sql) - опции, и они честно вынесены в отдельные пакеты.
3. **Где граница библиотеки?** Библиотека решает три вещи: что модель видит, что ей
   разрешено, что осталось в аудите. Модель, ACL, хранилище, UI, ретраи и идемпотентность
   остаются приложению. Граница проведена правильно, кроме одного места: `MemClaims` по
   умолчанию делает библиотеку хранилищем состояния одобрений.
4. **Failure, cancellation, retry, shutdown.** Отмена: `Run` ограничен `MaxWallTime`,
   `ExecuteApproved` намеренно отвязан от отмены запроса через `context.WithoutCancel`.
   Retry: у модели, с ограниченным backoff и уважением к `ctx`. Shutdown: у langfuse есть
   `Close` с дедлайном, у ядра состояния нет. Всё три ведут себя правильно.
5. **Кто владеет горутинами?** Единственная фоновая горутина в репозитории - `Sink.loop`
   в langfuse, у неё есть владелец (`Close`), `WaitGroup` и отмена. `goleak` в тестах нет,
   и это стоит добавить именно к ней.
6. **Какие дефолты безопасны?** Почти все: пустой набор меток = Untrusted, нулевой
   `Access` отвергается, отсутствие audit - ошибка. Требуют явного включения: `InsecureTLS`
   в gigachat (правильно) и `SendPrincipalID` в langfuse (правильно). Единственный
   небезопасный дефолт - пустой `Resource.TenantID` (HIGH-1).
7. **Что при 10x нагрузке?** Ядро выдержит, оно stateless и аллоцирует около 7 КБ на tool
   call. Первым упадёт `MemClaims` (HIGH-5), вторым - синхронный audit sink (HIGH-6).
   Оба лечатся конфигурацией, если о проблеме написано в документации.
8. **Какой тест доказывает главное?** `TestUngroundedCallDoesNotReachTheAuthorizer` и
   `TestExecuteApprovedRejectsAForgedPendingAction` - да, доказывают свойства, а не вызовы
   функций. Не хватает одного: сквозного теста Task + Flow + approval (BLOCKER-5).
9. **Понятен ли API через год без автора?** Ядро да. `flow` с `Suspension` без подписи и
   `Provenance` без `Sensitivity` - нет, придётся восстанавливать модель угроз по коду.

# Приложение. Имя для класса действия

Решение: **`Operation`**. Переименование выполнено. Ниже разбор вариантов, по
которому оно принималось.

Оспоренный пункт: в MEDIUM-1 я предлагал вернуться от `Access` к `Effect`. Возражение
справедливо, `Effect` неточен. Но и `Access` неточен, только в другом месте. Ниже пять
вариантов и цена каждого.

## Что именно именуется

Закрытое множество `{Read, Write, Send, Delete, Compute}` объявлено на инструменте и
участвует в одном месте: Gate строит из него потолок доступа с учётом целостности
аргументов. Свойство, которое нужно назвать, это **класс действия инструмента**. Не
право, не разрешение, не факт вызова.

## A. `Effect`

Обещает: «что произойдёт с миром, если это выполнить». Для `Write`, `Send`, `Delete`
читается точно, и главное — его невозможно прочитать как разрешение: `Effect: Write`
никогда не звучит как «этому можно писать».

Ломается на двух значениях из пяти. У `Read` эффекта нет, и `EffectRead` — внутреннее
противоречие. У `Compute` тоже. Это не педантизм: именно эти два значения открывают
список, и первое впечатление от поля создаётся по ним. Плюс в Go «effect» тянет за собой
эффект-системы (`IO`, `ZIO`), а не класс риска.

Вердикт: семантика правильная, слово уже́ уже, чем множество. Годится, но не лучший.

## B. `Access` (текущее имя)

Обещает: «какой доступ выполняет инструмент». Опирается на реальную практику: в AWS IAM
колонка _Access level_ описывает ровно класс действия (`Read`, `Write`, `List`, `Tagging`,
`Permissions management`), а не выданное право. Все пять значений читаются однородно,
включая `AccessCompute`.

Проблема в одном месте, но важном: поле живёт рядом с `Permission` в одном литерале.

```go
Tool[Args, R]{
    Access:     gobellim.Write,   // что инструмент делает
    Permission: "orders:refund",  // какое право нужно
}
```

Два соседних поля, оба звучат как разрешение. Читатель может взять `Access: Write` за
«этому инструменту разрешено писать», то есть ровно за то заблуждение, против которого
построен Gate. В аудите `"access": "write"` рядом с `"permission"` даёт ту же путаницу.

Вердикт: приемлемо, но оставляет ловушку в самой читаемой строке API.

## C. `Operation`

Обещает: «какой класс операции выполняет инструмент». Все пять значений читаются
однородно и без противоречий: `Operation: Read` — это чтение, а не «эффект чтения».
С `Permission` не конфликтует: операция и право — разные вещи в любом языке. В аудите
`"operation": "write"` и `operation=write` в логе читаются как факт.

Цена: слово перегружено в двух направлениях. Google AIP-151 называет `Operation`
долгоживущую задачу, а gRPC и REST — эндпоинт. Senior-читатель сначала подумает про
in-flight вызов, потом поправится по позиции поля: на объявлении `Tool` «операция» может
означать только класс инструмента. Это единственная реальная слабость варианта, и она
снимается контекстом.

Вердикт: рекомендую.

## D. `Action` и `ActionKind`

Слово уже занято экземпляром, а не классом: `PendingAction`, `ActionDigest`,
«approved action» в каждом абзаце документации. `Action: Write` будет читаться как «это
действие является write-действием», что почти правильно и потому особенно опасно.

Вердикт: отклонить из-за коллизии.

## E. `Capability`

В security «capability» — это предъявительский мандат: в этой библиотеке capability
являются handle set и подписанный `PendingAction`. Назвать так класс действия значит
создать второе значение слова в одном пакете. Вдобавок «capability» сильнее, чем
`Access`, намекает на выданное полномочие.

Вердикт: отклонить.

## F. Ортогональные булевы поля

`Mutates bool`, `SendsData bool`, `Irreversible bool`. Точнее по осям, но заменяет один
закрытый enum тремя политиками, которые автор комбинирует в голове, а матрица Gate
разрастается до восьми случаев. Булев флаг, включающий политику, — известный способ
получить небезопасный конфиг.

Вердикт: отклонить.

## G. `Verb`

Все пять значений — глаголы, и `Verb: gobellim.Write` буквально точен. Отклоняю за
щегольство: читателю нужно разгадать метафору, а clarity в Go Style Guide стоит выше
остроумия.

Вердикт: отклонить.

## Выбор

Итог: `Operation` лучше `Access` и лучше `Effect`, потому что точен в обоих местах, где
рождается ошибка. `Effect` неточен на `Read`/`Compute`, `Access` неточен рядом с
`Permission`. `Operation` не ломается ни там, ни там.

Если решено не платить за переименование, оставляйте `Access`: он ближе к AWS и уже
стоит в коде. Худший из трёх вариантов — вернуться к `Effect`.

Объём переименования: тип, пять констант, поля `Tool`, `Event`, `ToolCallRecord`,
`ApprovalCard`, JSON-ключ `access` → `operation`, атрибут в `SlogSink`, около тридцати
мест в тестах и примерах, все документы. Один механический коммит, отдельно от смысловых
правок.
