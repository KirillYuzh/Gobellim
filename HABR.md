# LLM, Go и guardrails: если бы работа с LLM была простой бизнес-логикой

Привет, habr! Меня зовут Кирилл. Сегодня я покажу Gobellim — Go-библиотеку для безопасной работы с языковыми моделями.

# TL;DR

Фреймворки супер, но только для сложных сценариев. Для автоматизации бизнес-процессов нужно внедрять работу с LLM напрмяую в ключевые сервисы и делать это точечно и безопасно. Gobellim позволяет реализовать бизнес-логику в одном use-case с гарантированным контролем безопасности.

Статья опирается на два тезиса:

1. Современные фреймворки в погоне за функционалом создают абстракции, но не безопасность. Это провоцирует создание guardrails как надстроек над ними. Как итог, даже с корпоративными возможностями получаются разрозненные и часто хрупкие решения для python/typescript.
2. Трудности использования LLM из обычного микросервиса. Из-за той же погони за фичами становятся популярными именно фреймворки (LangChain, Mastra, CrewAI...). Чтобы написать несложный сценарий с парой инструментов и одним workflow недостаточно просто добавить ещё один use-case. Приходится добавлять новый сервис/менять старый/переписывать часть логики и тд. Это создаёт неянвый technical gap.

# Давайте добавим ИИ 👍🏻

Я никогда не видел, чтобы работу с LLM встраивали в обычный микросервис. И почему вообще добавить один сценарий с LLM стоит так доорого?

Я выделил основные моменты:

- безопасность (написание guardrails)
- трейсинг
- реализация RBAC
- зависимость от Python и TypeScript

Может показаться, что зача решается несложно:

- обращаться к центральному сервису валидации при каждом запросе (guardrails ✅)
- отправлять данные в корпоративный LangFuse и grafana (трейсинг ✅)
- перенаправлять трафик через middleware/auth прокси (определение ролей ✅)

А дальше всего лишь написать через LangChain middleware для каждого tool, чтобы отдавать только разрешённые инструменты, провалидировать все возможные опасные входные данные и тд.

Я думаю, вы уже поняли, к чему я веду 💀

Мне не нравится:

- почти навярняка хрупкая ручная валидация входных данных
- по-неудобному одинаковый код в разных сервисах с LLM
- зависимость от реализации guardrails
- зависимость от LangFuse

Я решил, что это всё кринж и нужно могнуть этот сценарий.

# Прочитали OWASP и фантазируем 🛡️

### ~~Все дороги ведут~~ Одна дорога в Рим

Что нас беспокоит? PII, промпт инъекции... Перед попаданием в LLM запрос проходит одни и те же шаги, причём независимо от того, откуда данные. Тогда почему бы нам не заставить их идти по этому маршруту гарантированно, причём сделать это базовым сценарием без согласия разработчика?

Отлично, теперь каждый запрос к модели и вызов инструмента проходит через маршрут:

PII и маскирование -> Классификатор проимпт инъекций -> модель/инструмент -> обратное максирование (при необходимости).

### RBAC и ACL

Мне не нравится писать middleware для инструментов. Это скучно, можно легко ошибиться, неудобно поддерживать и читать. Давайте вместо этого напишем один YAML с deny-by-default?

```yaml
version: 1
default: deny

roles:
  user:
    permissions: [chat, search, "tool:kb_search"]
  support:
    permissions: [search, memory]
```
