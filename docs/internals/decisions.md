# Решения и допущения

Страница фиксирует границы v1, журнал принятых решений и допущения, которые
ещё предстоит проверить. Журнал решений ведётся в формате ADR: каждое решение
хранит обоснование и отвергнутую альтернативу.

## Границы v1

**Входит:** локальные и API LLM (vLLM, Ollama, OpenAI-compatible, GigaChat);
локальные (ONNX под тегом `ort`) и удалённые эмбеддинги; токенный чанкер;
ingest и гибридный поиск в ES (BM25 + kNN, RRF в Go); RBAC в YAML; guard с
одной моделью gliner-guard-omni и детерминированным слоем; tool calling с
вычитанием запрещённых tools и эффектами инструмента (egress, approval),
именованные хуки (`BeforeToolCall`/`AfterToolCall`); типизированные
последовательные пайплайны `flow` с suspend/resume; SSRF-защищённый инструмент
`webfetch`; бюджет хода; трейсинг в ES по модели [Langfuse](https://langfuse.com/) с сэмплированием и явной
политикой текста; детерминированные eval-проверки трейсов; дашборды Grafana;
деградация guard по рельсам (`Config.GuardFailOpen`), стоимость по `Config.Pricing`, право `chat`
и идентичность модели эмбеддера (`embed_model`).

**Входит также (часть 2.1):** память в ES — история треда, семантический recall
по resource и структурная (working) память; `Chat` умеет `ThreadID`.

**Входит также (часть 2.2–2.6):** spotlighting результатов
инструментов (`Config.Spotlight`); rate limit на тенанта (`Config.RateLimit`);
атомарный ingest (`doc_version`, «сначала запись, потом удаление»); кэш
ответов без tools (`Config.ResponseCache`); OTLP-синк трейсов
(`trace.NewOTLP`); стриминг ответа `ChatStream` со скользящим окном рельса
`output`.

**Входит также (часть 3):** сужение `flow` до одного `Step` с suspend/resume
(`D47`); `App.Health()` по writer-очереди и `HealthChecker` компонентов (`D48`);
реранкинг (`rerank.Reranker`, `SearchRequest.Rerank`, `D49`); необязательный
лексический поиск по инструментам (`Config.ToolSearch`, `D50`); клиент MCP
(stdio и streamable HTTP) с регистрацией инструментов как
`mcp:<server>:<tool>` (`D51`); MCP-сервер и `App.CallTool` (`D54`); разделение ролей
документации (`D52`).

**Не входит:** мультиагентность; workflows как граф/builder-DSL
(`flow` — один шаг, `D31`/`D47` — сужение); ABAC;
UI для трейсов (есть CLI-ридер `demo/cmd/traces`); JSON-API чтения трейсов (не
реализован); несколько
хранилищ; удалённый guard; GPU-провайдеры ORT; обратимая анонимизация PII; Colang и
диалоговые рельсы; семантический (эмбеддинговый) поиск по инструментам (только
лексический); GPU-реранкер (только HTTP-сервер).

### Продолжение журнала: D21…D35

Решения D21…D30 живут в [Дизайне v1](./design.md) §4 и здесь не дублируются.
Они покрывают контракт ES-запроса (D21), guard-таблицу и каноникализацию (D22),
политику текста трейса (D23), sampling (D24), эгресс и Rule of Two (D25),
ошибку инструмента как результат (D26), версионирование guard (D27), разделение
L1/L2 по семантике и структуре (D28), `SchemaMode` (D29) и пакет `eval` (D30).

Решения D31…D46 ниже — сознательные сдвиги границ v1. Они не переписывают D1…D30.

| D60 | Окно детекции (`guard.Options.WindowChars`, дефолт `DefaultWindowChars` = 1024): текст длиннее сканируется перекрывающимися окнами                                                   | L2 видел только первые 512 токенов, поэтому инъекция в хвосте длинного результата инструмента проходила мимо модели — при том, что Rule of Two запрещает эгресс именно после недоверенного ввода                                        | обрезать то, что видит модель, до окна L2 (дешевле, но теряется содержимое); семплировать окна (вероятностно) |
| D61 | `ValidateOutput(true)` — fail-closed: результат, не совпавший со схемой `Out`, отдаётся модели как error-result, а ход помечается недоверенным                                       | warn-режим пропускал off-schema данные в контекст модели и никак не влиял на Rule of Two                                                                                                                                                | оставить только лог; сделать отказ фатальным (`ErrTool`)                                                      |
| D62 | Текстовые поля индексов (`text`, `content`) создаются с анализатором `russian`                                                                                                       | корпус русскоязычный, а `standard` почти не стеммит русские слова, поэтому BM25-половина гибрида работала хуже, чем могла                                                                                                               | мультиполе `text` + `text.ru`; конфигурируемый анализатор                                                     |

### Продолжение журнала: D63…D68

Эти решения закрывают дефекты, найденные при повторной вычитке guard: смещения
маски, потоки слоёв, роль группы классификации и ключ кэша вердиктов. D67 —
не дефект, а решение о границе ядра.

| #   | Решение                                                                                                                                                                                                                              | Обоснование                                                                                                                                                                                                                                                                           | Отвергнуто / прежняя граница                                                                                                              |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| D63 | Находки даны в координатах исходного текста: `canonicalizeMap` отдаёт диапазон исходных рун для каждой канонической руны, находки L1 переводятся обратно (`remapSpan`)                                                               | каноникализация удаляет zero-width/bidi и склеивает последовательности, поэтому канонические смещения, применённые к исходному тексту, не совпадали с ним: маска недокрывала совпадение и выпускала хвост значения (телефон с zero-width отдавал лишнюю цифру) — прямой safety-дефект | считать, что каноникализация сохраняет число рун (`TestCanonicalizePreservesRuneCount`); маскировать канонический текст (ломает исходный) |
| D64 | Слой читает текст как есть, если объявляет `UsesNaturalText()`; L1 остаётся на каноническом тексте, L2 получает исходный                                                                                                             | каноникализация транслитерирует (регистр и кириллические гомоглифы → латиница), и модель, обученная на естественном тексте, на таком вводе ошибается: безобидная русская фраза получала `unsafe` 0.508 → ложный reject, который вдобавок скрывал реальную цену окна                   | один канонический поток для обоих слоёв (I-03 в прежней формулировке); L2 на каноническом тексте ради единообразия                        |
| D65 | Роль группы классификации и её порог читаются из экспорта: у информационных задач (`intent`, `tone`, …) немаппленная метка вердикта не даёт, у задач про безопасность — fail-safe `UNSAFE`; `thresholdFor` учитывает `cls_threshold` | без этого богатый экспорт отклонял безобидные «instructional»/«distressed»/«transactional», а поле `cls_threshold` молча игнорировалось (порог всегда был дефолтным 0.5)                                                                                                              | выводить «безопасность задачи» из имён меток; оставить немаппленную метку всегда `UNSAFE`                                                 |
| D66 | Кэш вердиктов ключуется инспектируемым текстом и версией guard, а не каноническим текстом                                                                                                                                            | находка несёт смещения в исходном тексте, поэтому вердикт — функция исходного текста: два текста с одной канонической формой, но разной раскладкой рун (`a` и `a\u200bb`) делили запись, и второй получал маску не по своим смещениям                                                 | ключ по каноническому тексту (I-02 в прежней формулировке)                                                                                |

| D67 | `flow` и `eval` остаются в ядре. `eval` — ноль внешних зависимостей (только stdlib, `internal/core` и `trace`); `flow` — `internal/core` и ровно две внешние библиотеки (`invopop/jsonschema`, `santhosh-tekuri/jsonschema/v6`) ради валидации схем `In`/`Out` | измерено `go list -deps` (2026-10-16): у `eval` внешних модулей нет вовсе, у `flow` — 7 транзитивно (2 прямых + `bahlo/generic-list-go`, `buger/jsonparser`, `pb33f/ordered-map/v2`, `go.yaml.in/yaml/v4`, `golang.org/x/text`). Утверждение «нулевые зависимости» верно для `eval` и **неверно** для `flow`; оно исправлено здесь, чтобы границу ядра не переоценивали. Оба пакета держат в ядре то, что обязано работать без сети и без ML: `flow` валидирует вход и выход шага по схеме до выдачи модели, `eval` даёт детерминированные проверки (без стоимости, без сети, без LLM-судьи — D30) | вынести оба в плагин за тегом сборки (тогда они выпадают из `go build ./...` и из gate, который их же проверяет); переписать валидацию схем вручную (дешевле по импортам, но теряется проверенный валидатор); оставить формулировку «нулевые зависимости» для обоих |
| D68 | Недоверенность хода определяется происхождением данных, а не вердиктом детектора: любой результат инструмента (retrieval, `webfetch`, MCP) помечает ход `untrusted` **всегда**, снять недоверенность инструмент не может | вердикт-зависимый taint оставлял ход доверенным, когда L2 пропускал вредоносный результат инструмента, и Rule of Two (BR-51) не срабатывал — прямой обход защиты от эксфильтрации, найденный в ревью (session.md) | taint только по `Action != Allow`/усечению |

## Что нового (TRIZ, SIT, SCAMPER)

Три идеи, на которых сошлись все три метода (Merging/Universality, Task
Unification, Combine; Prior Action, Subtraction, Eliminate; Prior Action,
Attribute Dependency, Adapt):

1. **Единый примитив вызова** вместо пользовательских middleware: authz, guard
   и трейс неотделимы от вызова LLM, tool, эмбеддера и ES.
2. **Вычитание tools из схемы модели** плюс повторная проверка при исполнении.
3. **ACL при записи + фильтр принципала внутри kNN** (аналог row-level
   security).

Проверка prior art ограничена: поиск по доступным публичным источникам показал
близкие по духу проекты на Go ([galdor](https://github.com/YasserCR/galdor), [Eino](https://github.com/cloudwego/eino), [langchaingo](https://github.com/tmc/langchaingo)), но связки «RBAC в
YAML + только ES + локальный guard + трейсы в той же ES» не нашёл. Это не
юридическое заключение о новизне; для патентных целей нужен профессиональный
поиск.
