# Бизнес-правила

Правила, которые изменение кода обязано сохранять. Каждое правило
пронумеровано (`BR-xx`); ID не переименовываются и не перенумеровываются.
Правило без пометки о слое действует в детерминированном слое.

Это единственное место, где описано **поведение** (`D52`): **сигнатуры** — в
[Дизайне v1](./design.md), **раскладка пакетов** — в [Архитектуре](./architecture.md).

Таблица sentinel-ошибок живёт в [Ошибках](../reference/errors.md), значения по
умолчанию и лимиты — в [Конфигурации](../reference/configuration.md).

Метки в колонке «Источник»: `архитектура` — [Архитектура](./architecture.md),
`решения` — [Решения и допущения](./decisions.md), `demo` —
[demo](../../demo/README.ru.md).

## Принципы

- **Один примитив вызова.** Любой вызов LLM, tool, эмбеддера и ES идёт через
  `internal/call`: `authz → guard → span → fn`. Пользователь middleware не
  пишет, обойти политику нельзя (D1).
- **Deny-by-default.** Нет явного разрешения — операция отклоняется. Это
  касается и RBAC, и ACL при поиске (D3, D4).
- **Детерминированный слой раньше ML.** RBAC, валидация аргументов, ACL и
  лимиты не зависят от модели; рельсы, оценённые моделью, обходимы (D4, D5,
  архитектура).
- **Маскирование PII необратимо для модели.** Модель видит заглушки вида
  `[PII:SNILS]`; реальные значения доходят только до инструментов, которые явно
  включили `AllowPII`, и только при однозначном отображении заглушки (`BR-04`).
- **Fail-closed по умолчанию.** Недоступность guard отклоняет операцию
  (`ErrGuardUnavailable`). Явный opt-out — `Config.GuardFailOpen`: на перечисленных
  рельсах упавший ML-слой пропускается, вердикт помечается `guard_degraded`
  (I-16, `D73`).
- **Одна БД и один guard.** Только ES (D11, D11); одна guard-модель за
  интерфейсом `guard.Detector` (D6).

- **Память — часть политики.** Память ограничена парой `tenant` + `user_id`
  принципала; `thread_id` от вызывающего сам по себе доступа не даёт (I-17).

| BR-107 | Отказ по политике — security-событие: отказ RBAC по инструменту (`tool_denied_rbac`) и отказ эгресс-политики (`egress_after_untrusted` / `egress_without_allowlist` / `egress_host_not_allowed`) пишутся через `Config.Logger` на уровне WARN (сообщение `kit: security event`; поля `event`, `tool`, `user_id`, `tenant`, `err`). Ход при этом прерывается (I-11). | детерминированный | BR-17, BR-51 |
| BR-108 | Батч инструментов из одного сообщения модели идёт параллельно только если он **целиком** read-only (`EffectRead` без `RequireApproval`) — тогда порядок вызовов не несёт смысла. Батч с любым `Write`/`Egress`/approval исполняется последовательно, чтобы побочные эффекты и подтверждения сохраняли порядок модели и не перемешивались. Параллелизм ограничен (`maxToolConcurrency` = 8), результаты возвращаются в порядке вызовов модели, первый фатальный отказ отменяет остальные. | детерминированный | D79 |
| BR-109 | `Config.GuardL2` обязателен: `nil` даёт `ErrInvalidConfig`, а L1-only запрашивается явно через `guard.L1Only()`. При `L1Only()` `New` пишет warning, а `Health` несёт `GuardLayers` (имена слоёв) и `GuardL1Only`. | детерминированный | D80 |
| BR-110 | Авторизация идёт раньше лимита: операция проверяет право принципала (`Authorize`) **до** `RateLimit`, поэтому отказ не расходует квоту тенанта. `Chat`/`ChatStream` проверяют право `chat` сразу после получения принципала — до guard, памяти и recall; `CallTool` проверяет право инструмента до лимита. Лимит по-прежнему срабатывает до провайдера, ES и guard (BR-86). | детерминированный | D81 |
| BR-111 | Egress-allowlist матчится по **разобранным** строковым значениям аргументов инструмента: `egressHosts` декодирует JSON и обходит объекты и массивы, поэтому `https:\/\/host` и `\u003a` не обходят список (BR-51, BR-68). | детерминированный | D82 |
| BR-112 | `Ingest` идёт guard → эмбеддинг: чанки проходят guard первыми, эмбеддится **маскированный** текст, а карантинный чанк не эмбеддится вовсе. `Search` прогоняет запрос через рельс `input`: `Reject` → `ErrGuardReject`, `Mask` — то, что уходит в эмбеддер, BM25 и трейс (BR-03, BR-04). | детерминированный | D83 |
| BR-113 | `Doc.ACL` обязателен и непустой: пустой ACL (или ACL из одних пустых строк) — `ErrInvalidArgs` ещё до эмбеддинга и guard, потому что deny-by-default-поиск всё равно не вернул бы такой документ (BR-13). Пробелы обрезаются, дубликаты схлопываются. | детерминированный | D83 |

## Потоки

### Chat

1. Создать trace, получить принципала из `context.Context` и проверить право `chat`
   сразу — до guard, памяти, recall и лимита операций (BR-07, BR-40, BR-76, BR-110).
2. Собрать историю: оставить только роли `user`/`assistant`, отбросить
   `tool_calls` и клиентские роли `system`/`tool` (BR-30).
3. Guard rail `input` по каждому сообщению: детерминированный слой → L2
   (BR-24…BR-27). Reject → `ErrGuardReject` без вызова модели (BR-25); PII →
   необратимая маска (BR-04). Любая маска или находка помечает ход как
   «видевший недоверенный ввод» для Rule of Two (BR-51); недоверенная строка
   истории или recall помечает его так же (BR-98, D59).
4. Вычислить доступные tools по роли через `authz` и вычесть запрещённые из
   схемы, передаваемой модели (BR-09, BR-16).
5. Цикл «модель → tools → модель», пока `steps < max_steps` (BR-20): вызвать
   модель (observation GENERATION); на последнем шаге `tool_choice` = `none`,
   чтобы модель отвечала, а не открывала вызов, который уже не исполнится. При
   `tool_calls` для каждого вызова — повторная проверка прав (BR-17), валидация
   args (BR-18, BR-19), лимиты `max_calls`/таймаут (BR-21, BR-22), approval по
   fingerprint (BR-53, BR-63), egress-политика (BR-51, BR-68), before-хук (BR-61),
   исполнение, after-хук (BR-61), guard результата — последним (BR-32, BR-62),
   `ValidateOutput`/`ModelView`, один ретрай при невалидных args (BR-23); результат
   добавить в контекст и пометить ход недоверенным (BR-101). Ошибка инструмента
   возвращается модели как результат (BR-50). Суммарные токены хода сверяются с
   `MaxTotalTokens` (BR-52).
6. Guard rail `output`: PII и секреты маскируются; INJECTION/UNSAFE
   записываются действием `Detect` без изменения текста (BR-56, rail output).
7. Завершить trace: trace и observations уходят в очередь асинхронного писателя
   (BR-42, BR-44).
8. Вернуть полный ответ; стриминг — через `ChatStream` (BR-89, BR-90).

Память (BR-81…BR-84): при заданном `ChatRequest.ThreadID` шаг 2 дополняется
загрузкой истории треда (`MemoryLoad`, последние `MemoryLimit` сообщений) перед
новым ходом; при `MemoryRecall > 0` и наличии эмбеддера в системное сообщение
добавляется блок recall; после успешного хода сообщения хода и ответ дописываются
через `MemoryAppend`. Ошибка recall не роняет ход.

Стриминг (BR-89, BR-90): `ChatStream` — тот же ход, но рельс `output`
применяется к скользящему окну (400 рун, хвост 96 рун), а подтверждённые куски
уходят через канал до завершения ответа; отказ рельса даёт `Retract` и аборт
потока. Tools, RBAC, память, бюджет и трейс работают как в `Chat` (I-19, I-20).

### Ingest

1. Создать trace, получить принципала; `Tenant` обязателен (BR-40, BR-07, BR-49).
   `Doc.ACL` проверяется и нормализуется до эмбеддинга и guard (BR-113).
2. Чанкование документа по токенам с overlap (BR-36).
3. Guard: каждый чанк проходит guard первым; отклонённый пишется маркером
   `quarantined: true` без текста и вектора и **не эмбеддится** (BR-31, BR-05,
   BR-112).
4. Вычислить ACL при записи (tenant + roles, заданные вызывающим) и записать в
   каждый чанк (BR-10, BR-11, BR-14); посчитать эмбеддинги через `Passages()`
   только по **маскированному** тексту разрешённых чанков (BR-34, BR-112).
5. Удалить прежние чанки документа (`_delete_by_query` по `doc_id` + `tenant`):
   повторная индексация не должна оставлять хвосты.
6. Проверить размерность векторов и записать чанки в ES через `internal/call`
   (BR-01, BR-38).

### Search

1. Создать trace, получить принципала; `Tenant` обязателен (BR-40, BR-07, BR-49).
2. Guard rail `input` по запросу: `Reject` → `ErrGuardReject` без эмбеддинга и
   поиска, `Mask` → маскированный запрос идёт дальше (BR-03, BR-04, BR-112).
3. Эмбеддить запрос через `Query()` с обязательным префиксом (BR-34).
4. Построить kNN-запрос и BM25-запрос, каждый с ACL-фильтром принципала
   (tenant + roles), `quarantined: false` и необязательным фильтром метаданных
   `store.Filter`; deny-by-default (BR-12, BR-13, BR-57).
5. Выполнить оба запроса через `_msearch` и слить результаты алгоритмом RRF в
   Go (BR-37).
6. Вернуть top-k (BR-39).

## Матрица решений guard по rail

Три рельса: `input`, `output`, `tool_result`.

| Rail          | Детерминированный слой                                                                                                    | ML-слой (L2)                                                                                                                      | Действие                                                                                                                                                                                 |
| ------------- | ------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `input`       | L0/L1: фразы, regex, контрольные суммы RU PII; каноникализация и decode-and-rescan (BR-55); L1 видит канонический текст   | метки классификации (`safety`/таксономия) → `UNSAFE`/`INJECTION`; метки сущностей → `PII` (BR-27, BR-71); L2 видит исходный текст | INJECTION/UNSAFE → reject (`ErrGuardReject`); PII/SECRET → mask необратимо; иначе allow                                                                                                  |
| `retrieval`   | ACL-фильтр tenant + roles и `quarantined: false` внутри kNN и BM25; фильтр `store.Filter`; deny-by-default (BR-12, BR-13) | —                                                                                                                                 | чанк вне ACL или карантинный не возвращается; отклонённый чанк ложится в индекс маркером                                                                                                 |
| `execution`   | RBAC, JSON Schema со `additionalProperties:false`, лимиты args/steps/calls/timeout; ML не используется (BR-03)            | —                                                                                                                                 | нет прав → `ErrUnauthorized` (фатально); неизвестный tool, невалидные или большие args, `max_calls` и ошибка инструмента → результат-ошибка модели; исчерпан `max_steps` → `ErrMaxSteps` |
| `output`      | правила маскирования секретов и PII                                                                                       | PII → mask; INJECTION/UNSAFE → `Detect` (запись находки, текст не меняется)                                                       | PII/SECRET → mask; инъекция/unsafe → `Detect`; иначе allow                                                                                                                               |
| `tool_result` | результаты tools проверяются как `input` (fast-fail на инъекциях)                                                         | —                                                                                                                                 | reject → результат заменяется на `{"error":"result blocked by guard"}`; PII/секреты → mask                                                                                               |

> [!NOTE]
> Строки `retrieval` и `execution` — не рельсы guard: таких констант в пакете `guard`
> нет. ACL/карантин и RBAC/валидация аргументов проверяются напрямую (`store.Filter`,
> `internal/call`), минуя `guard.Pipeline.Check`, поэтому в трейсах рельсов с такими
> именами не бывает.

Деградация (I-16, BR-78): рельс из `Config.GuardFailOpen` при недоступности
ML-слоя не фатален — остаётся детерминированный результат, а observation несёт
`guard_degraded: true`. Рельс вне списка fail-closed. Детерминированный слой от
политики не зависит и обязателен всегда.
