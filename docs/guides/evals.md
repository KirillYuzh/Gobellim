# Eval-наборы: регрессии по трейсам

Этот гид — про эксплуатацию `eval`: как собрать детерминированный регрессионный
набор, подключить рекордер к `kit.App` и прогнать его в `go test` и в CI.
Проверки — чистые функции от записанного трейса, поэтому набор воспроизводим,
бесплатен и не ходит в сеть. Что такое `eval` по смыслу — [Концепции: Eval](../concepts/eval.md);
здесь — рецепты и грабли.

## Почему детерминированные проверки, а не LLM-судья

| Свойство            | `eval` (проверки)                      | LLM-судья                         |
| ------------------- | -------------------------------------- | --------------------------------- |
| Повторяемость       | побитовая: та же функция, тот же трейс | зависит от модели и сэмплинга     |
| Стоимость           | ноль                                   | токены на каждый прогон           |
| Сеть                | не нужна                               | нужен провайдер модели            |
| Аудит               | видно, _какое_ правило упало           | «модель поставила 3 из 5»         |
| Ложные срабатывания | нет                                    | «судья» дрейфует вместе с моделью |

Именно поэтому в `kit` детерминированные проверки узаконены как `D30`
([Решения](../internals/decisions.md)), а `eval` зависит только от `trace` и
`internal/**` — он не импортирует `kit` и запускается из `go test` без остального
модуля.

> [!NOTE]
> Детерминированные проверки — не отказ от качества, а его измеримая часть.
> LLM-судью можно добавить **сверху** как отдельный сигнал, но не как гейт в CI:
> он невоспроизводим.

## Подключить рекордер

`trace.Recorder` — потокобезопасный in-memory `trace.Sink`. Он добавляется в
`kit.Config.Sinks`, а писатель в Elasticsearch остаётся первым и основным
приёмником: трейсы продолжают уходить в ES, рекордер получает их копию.

```go
rec := trace.NewRecorder()

app, err := kit.New(ctx, kit.Config{
	ES: es, LLM: llm, Policy: policy,
	Sinks: []trace.Sink{rec}, // writer всегда первый; rec — дополнительный приёмник
})
```

Что стоит помнить при подключении:

- **Рекордер синхронный.** Трейс уходит в рекордер в `defer` операции `Chat`, а
  observations — по мере вызовов (`tracerAdapter.Observe`); форвард в дополнительные
  sinks делает писатель прямо из `Enqueue`. Поэтому сразу после возврата из `Chat`
  в рекордере уже лежит весь трейс — ждать флаша ES не нужно (в отличие от чтения
  из ES).
- **Рекордер видит те же маскированные тексты, что и ES** (маскирование делает
  guard до примитива `call`), но **не** экспорт-фильтр: `HideInput`/`HideOutput`
  и обрезка строк/массивов/глубины применяются только к ES-документу
  (`document()`), а в дополнительные sinks уходит исходная структура. Зато
  `Options.Processors` и отбрасывание при `Name == ""` действуют до форварда — то
  есть processor влияет и на рекордер.
- **Сэмплер отсекает и sinks.** `trace.Writer.Enqueue` проверяет сэмплер **до**
  форварда в дополнительные приёмники, поэтому при `SamplerRatio` рекордер увидит
  только сэмплированную долю. Для eval держите сэмплер `always` (значение по
  умолчанию при `Sampler == nil`).

## Как устроен `eval.Run`

```go
func Run(ctx context.Context, rec *trace.Recorder, cases []Case,
	run func(ctx context.Context, input string) error) []Result
```

| Шаг                           | Что происходит                                                              |
| ----------------------------- | --------------------------------------------------------------------------- |
| `rec.Reset()` перед кейсом    | кейс видит только свой трейс                                                |
| `run(ctx, c.Input)`           | ваш прогон (например, `app.Chat`)                                           |
| ошибка `run`                  | кейс падает **без** проверок, `Result.Err` обёрнут в `eval: case …: run: …` |
| `Recorded(rec)`               | последний трейс и его observations                                          |
| проверки по порядку           | каждая, что вернула не `nil`, добавляется в `errors.Join`                   |
| `nil` в списке `Checks`       | кейс падает (`check N is nil`), остальные проверки не считаются             |
| `rec == nil` или `run == nil` | кейс падает с `core.ErrInvalidConfig`                                       |

Кейсы выполняются **последовательно** — параллелизма нет, рекордер один.

`Recorded` возвращает **последний** трейс из снимка и observations, чей `TraceID`
ему равен. Отсюда два следствия: (1) если `run` делает больше одного `Chat`,
проверится только последний; (2) если трейс не записан (сэмплер отсёк или `run`
ничего не вызвал), `Recorded` возвращает `eval: no trace recorded: core.ErrNotFound`.

## Проверки

`Check` — это `func(Trace) error`; `nil` значит «прошло».

| Проверка                           | Что проверяет                                            |
| ---------------------------------- | -------------------------------------------------------- |
| `Includes(s)` / `Excludes(s)`      | выход содержит / не содержит подстроку                   |
| `Equals(s)`                        | выход точно равен строке                                 |
| `Matches(re)`                      | выход совпал с `*regexp.Regexp`                          |
| `Similarity(want, min)`            | Dice-близость выхода и `want` не ниже `min`              |
| `DiceSimilarity(a, b)`             | сама метрика: Dice по биграммам **слов**                 |
| `CalledTool(name)`                 | инструмент вызван                                        |
| `DidNotCall(name)`                 | инструмент не вызван                                     |
| `UsedNoTools()`                    | не вызвано ни одного инструмента                         |
| `MaxToolCalls(n)`                  | вызовов не больше `n`                                    |
| `ToolOrder(names…)`                | имена встречаются в этом порядке (подпоследовательность) |
| `NoToolErrors()`                   | ни один инструмент не завершился ошибкой                 |
| `All(fs…)` / `Any(fs…)` / `Not(f)` | логические комбинации                                    |

Конвенции, на которых держатся проверки:

- **Текстовые проверки читают только `Trace.Output`** (финальный ответ),
  вход не инспектируется.
- **Tool-observation — это `Kind == SPAN`, имя = `Name`.** Guard пишется как
  `EVENT`, модель — как `GENERATION`, поэтому за инструменты они не считаются.
  Порядок — по `StartTime`.
- `NoToolErrors` считает ошибкой observation, у которой `Level == ERROR` **или**
  непустой `ErrorKind`.

## Рецепты

### Тест: модель вызвала нужный инструмент в нужном порядке

```go
func TestSupportBotToolOrder(t *testing.T) {
	ctx := context.Background()
	ctx = kit.WithPrincipal(ctx, kit.Principal{UserID: "u-1", Roles: []string{"user"}, Tenant: "acme"})

	rec := trace.NewRecorder()
	app, err := kit.New(ctx, kit.Config{ES: es, LLM: llm, Policy: policy, Sinks: []trace.Sink{rec}})
	if err != nil {
		t.Fatal(err)
	}
	defer func() { _ = app.Close(context.Background()) }()

	cases := []eval.Case{{
		Name:  "kb-then-ticket",
		Input: "Как вернуть товар и оформить заявку?",
		Checks: []eval.Check{
			eval.CalledTool("kb_search"),
			eval.ToolOrder("kb_search", "create_ticket"), // подпоследовательность, не обязательно подряд
			eval.MaxToolCalls(2),
			eval.NoToolErrors(),
		},
	}}

	results := eval.Run(ctx, rec, cases, func(ctx context.Context, input string) error {
		_, err := app.Chat(ctx, kit.ChatRequest{
			System:   "Ты ассистент поддержки.",
			Messages: []model.Message{{Role: model.RoleUser, Content: input}},
		})
		return err
	})
	if report := eval.Summarize(results); !report.OK() {
		t.Fatal(report.String())
	}
}
```

`ToolOrder` — именно **подпоследовательность**: лишние вызовы между
`kb_search` и `create_ticket` не мешают. Нужно строгое «сразу друг за другом» —
пишите свой `Check` (это `func(Trace) error`).

### Табличный набор через `All(...)`

`All` группирует проверки и одной строкой сообщает, сколько из них упало:

```go
cases := []eval.Case{
	{
		Name:  "return-policy",
		Input: "Сколько дней даётся на возврат?",
		Checks: []eval.Check{eval.All(
			eval.CalledTool("kb_search"),
			eval.NoToolErrors(),
			eval.Similarity("14 календарных дней", 0.5),
		)},
	},
	{
		Name:  "small-talk",
		Input: "Расскажи анекдот.",
		Checks: []eval.Check{eval.All(
			eval.UsedNoTools(),
			eval.Matches(regexp.MustCompile(`(?i)анекдот`)),
		)},
	},
	{
		// Любой из двух инструментов подойдёт.
		Name:  "weather-or-search",
		Input: "Что с погодой в Москве?",
		Checks: []eval.Check{eval.Any(
			eval.CalledTool("get_weather"),
			eval.CalledTool("kb_search"),
		)},
	},
}
```

Для действительно многих кейсов держите данные в `[]struct{...}` и превращайте
их в `[]eval.Case` в цикле — `Case.Metadata` для этого не нужен, он не влияет на
проверки.

### Golden-выход через `Similarity`

`Similarity` сравнивает выход с эталоном по Dice-близости биграмм слов. Это
устойчивее `Equals` к перестановкам и вставкам, но это **не семантика**:
парафраз с другими словами даст низкий балл.

```go
eval.Similarity("14 календарных дней с момента покупки", 0.6)
```

Ставьте порог по факту: прогоните набор, посмотрите `DiceSimilarity(got, want)`
на реальных ответах и отступите вниз. Для коротких ответов берите `Matches` или
`Includes` — они точнее.

### Прогон из CI

`eval` — обычный Go-код, поэтому набор это обычный `_test.go`. Ему нужны
**fakes**, а не сеть: поддельный `store.ES` (`Do(ctx, store.Request)`) и
поддельный `model.Client`. Обвязка CI уже гоняет тесты:

```yaml
# .github/workflows/ci.yml, джоба test
- name: go test
  run: go test ./... -count=1
```

Практика: держите eval-набор в отдельном файле (`bot_eval_test.go`) и запускайте
точечно `go test ./... -run TestSupportBotToolOrder -count=1`, а `-count=1`
важен, чтобы Go не отдал закешированный результат. Отдельного `-tags` для eval
не нужно: пакет собирается в сборке по умолчанию.

### Сэмплинг и стоимость рекордера

Рекордер in-memory и сам по себе бесплатен, но сэмплер **общий** с ES: он стоит
в `trace.Writer` и отсекает документы до форварда в дополнительные sinks.

| Хотите                    | Что делать                                                                                                          |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| Полный набор в тестах     | `Sampler` не задавать (значит `always`)                                                                             |
| Разгрузить ES в проде     | `Sampler: trace.SamplerRatio(0.1)` — детерминированно по `trace_id`                                                 |
| Тот же инстанс и для eval | Не совмещать: при ratio кейсы с выброшенным трейсом падают `no trace recorded`. Соберите отдельный `App` для тестов |

Решение сэмплера детерминировано по `trace_id` (`D24`), поэтому одна и та же
трасса сохраняется во всех процессах — но это не помогает eval «дёшево
сэмплировать фиксированный набор»: каждый кейс обязан оставить трейс.

## Частые ошибки

- **Проверяете текст, который guard замаскирует.** `Trace.Input` и `Trace.Output`
  уже прошли guard, поэтому `Includes("4111 1111 1111 1111")` упадёт: в тексте
  стоит заглушка `[PII:BANK_CARD]` (или похожая). Проверяйте заглушку или
  `Excludes` на исходное значение. Подробнее — [Guardrails](../concepts/guardrails.md).
- **Имя инструмента не совпало с зарегистрированным.** `CalledTool` сравнивает с
  `Observation.Name`, то есть ровно с именем, которое вы передали в
  `kit.Tool(app, "kb_search", …)`. Алиасы и «человеческие» имена не работают.
- **Пустой список observations.** `CalledTool`/`ToolOrder` для хода без вызовов
  дают отдельное сообщение `no tool observations recorded`, а `UsedNoTools`
  проходит. Это разные ветки — не путайте их при отладке.
- **`Recorded` возвращает только последний трейс.** Если `run` делает `Chat` +
  `Search`, проверится только последний (обычно `Search`). Разбейте на кейсы или
  проверяйте `rec.Snapshot()` руками.
- **`nil` в списке проверок.** Пустой `eval.Check` в `Checks` — это падение кейса
  (`check N is nil`), а не пропуск.

## Ограничения

- **Только детерминированные проверки.** Судить «смысл» ответа `eval` не умеет:
  `Similarity` — это Dice по биграммам слов, а не семантика; на парафразах и
  синонимах она слаба.
- **Только текст выхода и список tool-observations.** Проверок на латентность,
  стоимость, `usage` или на содержимое аргументов инструмента в пакете нет
  (`Result.Elapsed` есть, но ассертов на него — нет).
- **Один трейс на кейс.** Набор не умеет проверять сессию целиком: `Recorded`
  берёт последний трейс, а `Run` сбрасывает рекордер перед каждым кейсом.
- **Вход не инспектируется.** «Что реально ушло в модель после маскирования» из
  `eval` не проверить — для этого смотрите observations (`guard:input`, `EVENT`)
  через `rec.Snapshot()`.
- **Сэмплер общий с ES**, отдельной ручки «сэмплировать только рекордер» нет.
