# Стриминг

`Chat` возвращает ответ целиком: guard выхода должен увидеть полный текст до того,
как он попадёт к клиенту. Стриминг (`ChatStream`) сохраняет это свойство, но отдаёт
текст по мере появления — по **скользящему окну**, которое проходит рельс `output`
до эмиссии.

Стриминг — не второй путь исполнения, а расширение `Chat`: цикл инструментов, RBAC,
память, бюджет и трейс работают одинаково. Меняется только способ отдачи ответа
модели клиенту.

## Когда использовать

- Ответ длинный и пользователь ждёт первую строку, а не весь абзац.
- Модель отвечает прозой; **вызовы инструментов** стриминга не дают — цикл
  «модель → инструменты → модель» всё равно собирает tool-часть целиком.
- Провайдер умеет SSE: сейчас это `openai` и `vllm` (`*model.OpenAIClient`).

Не нужно, если ответы короткие: `Chat` проще, а guard всегда видит текст полностью.

## Быстрый старт

```go
ch, err := app.ChatStream(ctx, kit.ChatRequest{
	System:   "Ты ассистент.",
	Messages: []model.Message{{Role: model.RoleUser, Content: "Расскажи про ES"}},
})
if err != nil {
	return err
}
for c := range ch {
	if c.Err != nil {
		return c.Err
	}
	if c.Text != "" {
		fmt.Print(c.Text)
	}
	if c.Done {
		// c.Final.Content == весь выданный текст
	}
}
```

Канал **обязательно** вычитывать до закрытия: иначе фоновая горутина не
завершится. Требуется право `chat`, как и у `Chat`.

## Как это работает

### Скользящее окно

Guard не может проверить токенизированный поток целиком. Поэтому `ChatStream`
буферизует ответ и отправляет через рельс `output` не весь текст сразу, а **окна**
(`windowGuard`):

- `streamMinWindow` = `400` рун — минимальный размер окна, отправляемого в guard;
- `streamHoldback` = `96` рун — хвост, который **не** отдаётся клиенту и остаётся в
  буфере, чтобы совпадение на границе окна не проскочило;
- резка — по границе предложения (`\n`, пробел, `.`, `!`, `?`, `;`, `:`), а не по
  произвольному смещению.

Поток такой: накопили ≥ окна → отрезали по границе → прогнали кусок через рельс
`output` → отдали уже проверенный текст. Хвост остаётся до следующего окна (или до
конца ответа).

### Чанки

```go
type StreamChunk struct {
	Text    string // подтверждённый, уже проверенный текст
	Retract bool   // клиент отбрасывает показанное; поток завершится ошибкой
	Done    bool   // последний чанк, с собранным Final
	Final   model.Message
	Err     error
}
```

На чанк имеет смысл ровно одно из полей. Инвариант: `Done.Final.Content` равен
конкатенации всех выданных `Text` — то, что записано в память и трейс, совпадает с
тем, что увидел клиент.

### Отказ рельса

Если окно не прошло рельс `output` (например, нашлись секреты), приходит
`StreamChunk{Retract: true}`, а затем ошибка. Это значит: **отбросьте показанное**.
Так fast-fail сохраняется и в стриминге — «плохой» текст либо не уйдёт вовсе, либо
будет отозван.

### Откат

Если клиент LLM не реализует `model.Streamer` (например, `ollama` или `gigachat`),
`ChatStream` не падает: он вызывает буферизованный `Chat` и выдаёт один чанк `Text`
плюс `Done`. Вызывающий код не меняется — только ощущение потока пропадает.

## Цена и ограничения

- **Один проход guard на окно**, а не на весь ответ: дешевле по latency, но
  детекция видит текст частями.
- **Остаточное окно.** Совпадение длиннее `streamHoldback` (96 рун) без границы
  предложения внутри всё ещё может пересечь окно: начало уйдёт клиенту до того, как
  хвост дойдёт до guard. Это документированное ограничение (I-20), а не ошибка;
  для чувствительных сценариев используйте `Chat` (без стриминга).
- **Нет стриминга инструментов** и нет `Generate`-стрима: `Generate` буферизует
  результат, потому что его нужно декодировать целиком.
