# gobellim — DESIGN

> **Рабочее название:** `gobellim` — небольшая Go-библиотека для безопасного добавления одного LLM use-case в существующий микросервис.
>
> **Статус:** design draft v0.2. Реализованы P0 и P1 (см. §14); P2 — нет. Все показатели производительности — цели для проверки, а не измеренные результаты. API ниже описывает реализованную поверхность, кроме явно помеченных P2-частей.

## Кратко

`gobellim` — это встраиваемый execution и policy layer вокруг LLM. Он даёт разработчику типизированные `Task`, инструменты, RBAC/ACL, контроль происхождения данных, одобрение вне модели (foreign approval) и replay-тесты. Ядро не требует собственного сервера, БД, брокера сообщений или обязательного ML-классификатора.

Главный инвариант:

> **Модель может предложить текст, параметры или действие. Она не может сама выдать себе полномочия, изменить policy, зарегистрировать новый инструмент или исполнить побочный эффект в обход `Gate`.**

Библиотека не обещает абсолютную защиту от всех prompt injection. Она уменьшает риск тем, что недоверенный текст не является кодом управления, а любой model-initiated tool call проверяется обычным кодом приложения до выполнения.

## 1. Цели и не-цели

### Цели

| ID  | Требование                      | Решение                                                                                                                                                          |
| --- | ------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| G1  | Устойчивость к prompt injection | Недоверенный ввод не управляет control flow; все tool calls проходят через fail-closed `Gate`; свободный вывод модели консервативно tainted.                     |
| G2  | Минимум повторяющегося кода     | Один `Task[In, Out]`, Go-структуры с ограниченными тегами, зарегистрированные типизированные инструменты и переиспользуемые policy-интерфейсы.                   |
| G3  | RBAC и ACL                      | `Authorizer` адаптируется к существующей авторизации; объектные ACL проверяются до чтения данных и перед каждым действием.                                       |
| G4  | Workflow с foreign approval     | Типизированный последовательный workflow, `Suspended` / `Resume`, approval card с provenance и повторной проверкой прав.                                         |
| G5  | Встраиваемость                  | Ядро работает внутри процесса; модель, HTTP-обвязка, классификаторы, OTel и дополнительные Store подключаются отдельно.                                          |
| G6  | Маленький dependency footprint  | У core нет обязательных сторонних модулей и инфраструктурных сервисов. SQL-интеграция использует переданный приложением `*sql.DB` либо пользовательский `Store`. |
| G7  | Простое тестирование            | `FakeModel`, fake clock, подменяемые инструменты, проверки security-инвариантов и replay/diff политик.                                                           |
| G8  | Безопасное внедрение            | Сначала offline replay / dry-run; отдельно описана разница между наблюдением и реальным enforcement.                                                             |

### Не-цели

- Не полноценная платформа агентов, не самостоятельный IAM и не замена workflow-движку уровня Temporal.
- Не гарантия того, что модель не сгенерирует вредный текст или не будет обманута.
- Не замена бизнес-валидации, транзакций, rate limits и ACL существующего сервиса.
- Не обязательный LLM-классификатор для каждого запроса.
- Не универсальный DSL для промптов и диалоговых сценариев.
- Не обещание exactly-once для внешнего побочного эффекта при падении процесса: это требует поддержки идемпотентности или транзакционных гарантий на стороне получателя.

## 2. Модель угроз

### Доверенная база

Доверяем коду приложения, его конфигурации и зарегистрированным tool handlers; `Principal`, созданному после аутентификации; источникам policy; решению проверенного и авторизованного approver в рамках показанной ему операции.

**Не считаем доверенными:** ответы модели (включая структурированный JSON), пользовательский текст, документы и результаты поиска, письма, тикеты, страницы, ответы инструментов с внешними данными, аргументы tool call до валидации, свободный текст, сгенерированный моделью.

Пользователь может быть аутентифицированным и при этом отправлять недоверенное содержимое. Подлинность личности не делает текст инструкции безопасной и не доказывает право на объект.

### Атакующий может

1. Встраивать прямые или косвенные инструкции в пользовательский ввод, документы, retrieval-результаты и ответы инструментов, включая unicode-обфускацию и поддельные ролевые теги.
2. Пытаться менять ID ресурса, tenant, получателя, сумму, URL или другие аргументы tool call.
3. Провоцировать утечку доступного контексту секрета через ответ, внешний инструмент, URL или рендеринг markdown.
4. Повторять запросы, повторно использовать или подменять сохранённую приостановку, менять аргументы после одобрения, пытаться использовать nonce другого tenant или старой версии workflow.
5. Вызывать дорогие и долгие сценарии, раздувать контекст и число tool calls.

### Вне модели угроз

Компрометация процесса приложения, его конфигурации или хранилища claims; уязвимости в самом провайдере модели; злонамеренный субъект, обладающий правом одобрять операцию и обходящий внутренние организационные процессы. Four-eyes, quorum и аудит могут снижать, но не устраняют эти риски.

Граница исполнения — `Gate`, а не системный промпт, эвристический классификатор или самоотчёт модели.

## 3. Архитектурные инварианты

### 3.1. Код приложения управляет потоком

Workflow и разрешённые действия определены кодом Go. Модель может выбирать между зарегистрированными действиями и предлагать аргументы, но не может добавить инструмент, изменить policy или определить следующий произвольный шаг за пределами сценария приложения.

### 3.2. Каждый внешний эффект проходит через Gate

Ни один tool handler, зарегистрированный в `gobellim`, не вызывается напрямую из ответа модели. Gate валидирует типы и ограничения, проверяет полномочия, access, provenance, grounding и необходимость одобрения вне модели. Ошибка проверки приводит к отказу.

### 3.3. Метки не повышаются автоматически

Связь с недоверенным источником не исчезает от перефразирования, суммаризации или валидного JSON. `Validate` может только отказать: успешная проверка ничего не повышает. Единственное повышение целостности — решение доверенного источника вне модели (человека или бизнес-логики) об конкретном действии, и оно отражается в аудите.

### 3.4. Свободный вывод модели считается derived/untrusted

JSON-схема ограничивает форму, а не истинность или безопасность содержимого. Поля типа `string` из ответа модели остаются недоверенными. `oneof`, `bool` или ограниченный числовой диапазон ограничивают пространство возможных значений, но не делают выбор авторизацией и не отменяют проверки policy.

### 3.5. Детекторы могут ужесточить решение, но не выдать разрешение

Jailbreak/PII-классификаторы и эвристики могут добавить сигнал риска, вызвать маскирование или усилить решение до `Escalate`/`Deny`. Они не могут повысить целостность значения, подтвердить право доступа или переопределить `Gate` в сторону `Allow`.

### 3.6. `Audit` не маскируется под защиту

Наблюдение за решением и его enforcement — разные функции. Audit/replay показывает, что изменила бы новая policy, но не должен скрытно выполнять запрещённое действие. В production реальное действие всегда должно пройти действующую enforcing-политику. Для безопасного проигрывания используется dry-run с подменёнными tool handlers.

## 4. Архитектура и пакеты

```text
gobellim/
  engine.go             # конфигурация, task runtime, лимиты
  task.go               # Task[In, Out], модельный цикл
  model.go              # интерфейс модели и нейтральные DTO
  tool.go               # типизированный Tool и реестр
  principal.go          # principal из приложения; без собственной аутентификации
  labels.go             # provenance, integrity, sensitivity, readers
  gate.go               # единственная точка исполнения tool calls
  policy.go             # Authorizer, Decision, Access
  schema.go             # поддерживаемое подмножество тегов/валидации
  audit.go              # события и интерфейс Sink
  errors.go
  flow/                 # sequential workflow, suspension, resume
  plugins/langfuse/     # optional audit sink
  plugins/gigachat/     # optional GigaChat model adapter
  detect/               # необязательные сигнальные детекторы
  testkit/              # FakeModel, scripted tools, fake clock, malicious cases
  replay/               # replay policy decisions и diff
  model/httpjson/       # отдельный модуль/пакет адаптера модели на net/http
  httpapproval/         # необязательные handlers на net/http
  otel/                 # необязательный экспорт телеметрии
  store/sql/            # необязательный Store поверх database/sql
```

`flow`, `detect`, `httpapproval`, `otel`, `model/*` и `store/*` не должны создавать неявные зависимости core от своих внешних библиотек. В первом прототипе допустимо держать часть файлов в одном Go-пакете; границы на диаграмме — прежде всего границы ответственности.

Реализованы корневой пакет, `flow/`, `store/sql/`, `testkit/`, `plugins/langfuse/` и `plugins/gigachat/`. `detect/`, `replay/`, `httpapproval/` и `otel/` — P2 и в текущем дереве отсутствуют.


## 5. Публичная модель API

Публичный API должен быть маленьким, а бизнес-функции — оставаться обычными функциями микросервиса. Код ниже показывает направление дизайна; до MVP сигнатуры и имена ещё могут измениться.

### 5.1. Один use-case — один Task

```go
type TicketInput struct {
    // ID and tenant must come from authenticated application context,
    // not be trusted merely because they appear in user text.
    TenantID string `gobellim:"source=principal"`
    TicketID string `gobellim:"source=application"`
    Body     string `gobellim:"untrusted,sensitivity=pii"`
}

type TriageOutput struct {
    Category string `gobellim:"oneof=billing|technical|other"`
    Reply    string // free-form model text: remains untrusted-derived
}

engine, err := gobellim.New(
    gobellim.WithModel(model),
    gobellim.WithAuthorizer(existingAuthorizer),
    gobellim.WithAudit(auditSink),
    gobellim.WithLimits(gobellim.Limits{
        MaxInputBytes:  32 << 10,
        MaxOutputBytes: 16 << 10,
        MaxToolCalls:   3,
    }),
)
if err != nil {
    return err
}

task, err := gobellim.NewTask[TicketInput, TriageOutput](engine,
    gobellim.TaskConfig{
        Name:        "ticket.triage",
        Instruction: "Classify the ticket and propose a reply.",
        Tools:       tools,
    },
)
if err != nil {
    return err
}

res, err := task.Run(ctx, principalFromRequest(r), in)
// res.Status == gobellim.TaskCompleted or gobellim.TaskApprovalRequired
// res.Output is the typed Out value; res.Pending is the escalated action.
// After a trusted approver accepts it:
//   out, rec, err := task.ExecuteApproved(ctx, requester, approver, res.Pending)
```

Разработчик не должен передавать Principal внутрь prompt как обычный текст и ожидать, что модель корректно его сохранит. Principal передаётся runtime отдельным параметром, а policy проверяет его вне модели.

`gobellim.New` требует model, authorizer и audit sink: без любого из них — `ErrInvalidConfig`. `TaskConfig.FourEyes` требует, чтобы `ExecuteApproved` получил апрувера, отличного от requester'а; флаг записан в подписанную карточку, поэтому его нельзя снять с уже выданного `PendingAction`. В `flow` тот же Four-Eyes проверяется на `Resume`, где апрувер — аутентифицированный `Principal`, а не значение, которое передало приложение.

### 5.2. Типизированный инструмент

```go
type RefundArgs struct {
    OrderID string `gobellim:"required,ground"`
    Cents   int    `gobellim:"min=1,max=5000"`
}

type RefundResult struct {
    RefundID string
    Status   string
}

refundTool := gobellim.Tool[RefundArgs, RefundResult]{
    Name:       "orders.refund",
    Access:     gobellim.Write,
    Permission: "orders:refund",
    Target: func(p gobellim.Principal, a RefundArgs) gobellim.Resource {
        return gobellim.Resource{Type: "order", ID: a.OrderID, TenantID: p.Tenant}
    },
    Validate: validateRefundAgainstBusinessRules,
    Run: func(ctx context.Context, p gobellim.Principal, a RefundArgs) (RefundResult, error) {
        // Existing business logic; no direct model access here.
        return orders.Refund(ctx, p.Tenant, a.OrderID, a.Cents)
    },
}
```

Инструмент декларативно описывает access, permission, цель, дополнительные бизнес-ограничения и обработчик. `Access` — это класс операции, а не оценка риска: `Read`, `Write`, `Send`, `Delete`, `Compute`. Для всего, кроме `Compute`, `Target` обязателен: `NewTask` отклоняет инструмент без непустого `Resource`, иначе ACL молча выродился бы в RBAC. Регистрация не даёт модели права вызвать функцию напрямую: модель возвращает только имя и JSON-аргументы, а runtime находит инструмент в закрытом реестре и вызывает Gate.

### 5.3. Ограничения schema-by-tags

Теги нужны, чтобы не дублировать простые ограничения в нескольких местах. Встроенная генерация схемы поддерживает только документированное подмножество типов/тегов и должна отказывать на неизвестном или неоднозначном ограничении. Важные бизнес-правила остаются обычными валидаторами Go. Схема для модели никогда не заменяет повторную runtime-валидацию аргументов.

Поддерживаемое подмножество: `string`, `bool`, целые и дробные числа, срезы скаляров и вложенные структуры глубиной до двух уровней. Теги: `required`, `source=principal|application`, `sensitivity=public|internal|pii|secret`, `oneof=a|b`, `min`, `max`, `ground`, `ground=SourceField`, `ground=any`. `sensitivity=pii` маскирует совпадения, `sensitivity=secret` заменяет всё значение одним handle. `source` и `ground` применимы только к `string`, `sensitivity` — к `string` и `[]string`. Неизвестный тег, `map`, указатель, интерфейс, срез структур, `time.Time`, `[]byte`, встроенная struct без явного `json`-имени и вложенность глубже двух уровней отклоняются на этапе `NewTask`. `required` на `bool` запрещён: ноль неотличим от отсутствия. `required` на строке и числе означает ненулевое значение. `ground`-поле принимает только handle из объявленного входного поля; голый `ground` означает путь аргумента, `ground=SourceField` — другое поле, `ground=any` — явный opt-out. Сырая строка от модели не grounds аргумент, а handle в non-ground поле — `ErrUngrounded`.

`encoding/json`-путь должен ограничивать размер, отклонять неизвестные поля там, где это возможно, проверять обязательные значения и не принимать неограниченную вложенность/массивы без лимитов.

Те же `sensitivity`-теги читаются на **результате** инструмента перед отправкой в модель (`redact.go`): `secret` становится handle, `pii` маскируется. Редактор понимает структуры, срезы, массивы, `map` и указатели, а также `[]byte` и `map[string]string` с тегом `sensitivity`. Тип, который маршалит себя сам (`time.Time`, `json.Marshaler`), непрозрачен: `sensitivity` на нём — `ErrUnsupportedType` на `NewTask`, а не молчаливое отключение маскирования. Неизвестный `gobellim`-тег на результате — тоже ошибка `NewTask`.

## 6. Метки, provenance и handles

### 6.1. Разделяем целостность, чувствительность и аудиторию

```go
type Integrity uint8
const (
    Untrusted Integrity = iota
    Derived
    Trusted
)
```

type Sensitivity uint8
const (
Public Sensitivity = iota
Internal
PII
Secret
)

type Label struct {
Integrity Integrity
Sources []SourceRef
Sensitivity Sensitivity
}

````

`Integrity` описывает, насколько можно полагаться на значение как на основание для действия. `Sensitivity` задаёт ограничения раскрытия. `Readers`/per-reader ACL в текущей реализации **не реализованы**: библиотека не фильтрует данные по читателям, это делает приложение до передачи контекста в `Task`.

Метки могут автоматически только ухудшаться: `Trusted → Derived/Untrusted`, либо становиться более чувствительными. Автоматического повышения нет вообще: `Tool.Validate` — проверка на отказ и успехом ничего не повышает. Handle от модели остаётся `Untrusted`, а запись возможна только при `Trusted`-метке, то есть из поля, помеченного `source=application`. Единственное повышение — решение доверенного апрувера об конкретном действии (`ExecuteApproved`), и оно отражается в аудите отдельным `rule_id`.

### 6.2. Не обещать точный data-flow tracking внутри LLM

Runtime не может достоверно восстановить, какая часть свободного ответа модели зависит от какого слова контекста. Поэтому если модель видела недоверенный текст, её свободные текстовые ответы и сформированные из них аргументы маркируются консервативно как `Derived` с объединённым набором релевантных источников. Поле с `oneof` может быть ограничено по форме, но для использования в чувствительном действии всё равно проходит grounding и policy.

Пользовательские строки по умолчанию — не доверенные управляющие данные. Значения вроде order ID, recipient или tenant подтверждаются через приложение/Principal, ACL и allowlisted directory, а не одной проверкой, что строка где-то встречалась в тексте.

### 6.3. Opaque handles

Для секретов, PII и идентификаторов, которые модели необязательно видеть в исходном виде, runtime может заменять значение непрозрачным handle (`<h17>`). Handle хранится в локальном для run реестре с label, provenance, readers и sensitivity.

Модель должна возвращать именно существующий handle, если параметр должен ссылаться на ранее известное значение. Выдуманный handle считается ungrounded. Разыменование выполняется только внутри Gate после проверки политики; в произвольный prompt или лог исходное значение не вставляется.

Handles — не замена ACL и не способ полностью скрыть данные, которые модели действительно необходимы для понимания. Необходимо минимизировать содержимое контекста: не передавать секреты, которые не нужны задаче.

### 6.4. Grounding

Аргумент считается grounded только если его происхождение подтверждается конкретным полем из доверенного состояния приложения:

- значение пришло через существующий handle, созданный для этого запуска;
- handle пришёл из объявленного входного поля (`ground` или `ground=SourceField`);
- `Tool.Validate` подтверждает бизнес-смысл — но только как отказ, не как повышение.

Handle в непомеченном `ground` поле — `ErrUngrounded`, даже если такой handle существует. `ground=any` — явное ослабление, не дефолт: для нормального сценария достаточно объявить источник.

`Tool.Validate` выполняется после authz и до потолка access. Lookup в allowlisted directory — это и есть `Validate` приложения; библиотека не ходит в чужие данные сама и не повышает метку по результату lookup.

Совпадение строки с фрагментом недоверенного документа **не** делает её доверенной. Даже существование такого order ID в directory не даёт права действовать с ним: ACL и business policy всё равно обязательны.

## 7. Gate: RBAC, ACL и решение по действию

### 7.1. Контракт авторизации

```go
type Authorizer interface {
    Allowed(ctx context.Context, p Principal, permission string, resource Resource) (bool, error)
}
````

Этот интерфейс адаптируется к существующей системе ролей/политик приложения. Для локального демо может быть простая in-memory RBAC-политика, но библиотека не требует переносить users/roles/ACL в новое хранилище. `Authorizer` обязателен: `New` без него — `ErrInvalidConfig`.

- RBAC проверяет разрешение роли на действие.
- ACL/ABAC проверяют конкретный ресурс, tenant, владельца и условия доступа.
- Data ACL применяется **до** добавления документа в контекст модели.
- Авторизация инструмента проверяется заново перед фактическим вызовом и после approval Resume.
- Ошибка `Authorizer` — `Deny` (fail-closed).
- `Principal` берётся из аутентифицированного контекста приложения; текст модели никогда не может его изменить.

### 7.2. Единое решение

```go
type DecisionKind uint8
const (
    Deny DecisionKind = iota
    Allow
    Escalate
)

type Decision struct {
    Kind    DecisionKind
    RuleIDs []string
    Reason  string
}

Decide(principal, tool, canonicalArgs, labels, currentPolicy)
    -> Deny | Allow | Escalate
```

Решение учитывает пересечение:

`RBAC ∩ ACL(resource) ∩ access ceiling(integrity) ∩ grounding(args) ∩ business limits`.

Решение — детерминированный код. Модель не может ответом «я проверил права» переопределить его.

### 7.3. Access и базовая policy-матрица

Каждый инструмент объявляет класс операции:

- `Read` — чтение данных;
- `Write` — изменение состояния;
- `Send` — передача данных внешнему получателю (эксфильтрация — тоже `Send`);
- `Delete` — удаление;
- `Compute` — чистая работа без данных и без цели (расчёт, форматирование).

`Access` не имеет разрешающего zero value: `AccessUnknown` отклоняется на `NewTask`, поэтому забыть access нельзя. Для всего, кроме `Compute`, `Target` обязан вернуть непустые `Type` и `ID`; пустая цель — `Deny` с правилом `target-unbound`. Gate также требует, чтобы `Resource.TenantID` (пустой заполняется из `Principal.Tenant`) совпадал с tenant принципала, и проверяет это до `Authorizer`.

Порядок проверок: tenant binding → grounding → `Authorizer` → `Tool.Validate` → потолок access. Grounding идёт раньше ACL, чтобы id ресурса, придуманный моделью, не дошёл до `Authorizer` (и не попал в его аудит), а авторизация — раньше `Validate`, чтобы бизнес-правило не запускалось для вызывающего, который всё равно не смог бы выполнить действие. Каждая проверка fail-closed.

Стартовая матрица — conservative defaults, затем её можно ужесточить policy приложения:

| Худшая целостность аргументов | Read  | Write    | Send  | Delete   | Compute |
| ----------------------------- | ----- | -------- | ----- | -------- | ------- |
| `Trusted`                     | allow | allow    | allow | escalate | allow   |
| `Derived`                     | allow | escalate | deny  | deny     | allow   |
| `Untrusted` / нет меток       | allow | escalate | deny  | deny     | allow   |

`Trusted` достижим только из поля с `source=application` — модель не может его получить, добавив свободный текст или handle. `worst` считается по всем аргументам, поэтому один model-derived аргумент в write-вызове всё равно приводит к `Escalate`, а в `Send` — к `Deny`.

`Escalate` не значит «апрувер может разрешить всё». Это переход к проверке конкретного действия вне модели (человеком или бизнес-логикой); базовые ACL, лимиты, schema и законность действия остаются обязательными. `Task.ExecuteApproved(ctx, requester, approver, pending)` после одобрения перепроверяет tenant, RBAC/ACL, `Validate`, tool/access и digest аргументов, а потолок access заменяет решением апрувера; `approver` попадает в audit как `approval.granted`. Одобрение одноразовое: `nonce` из `PendingAction` уходит в `ClaimStore` (процессный по умолчанию, общий через `WithClaimStore` или `store/sql`), второй вызов даёт `ErrApprovalReplay`.

### 7.4. Send и data ACL

Любая передача данных наружу — отдельный access `Send`. Текущая реализация проверяет только потолок по целостности аргументов: `Send` разрешён при `Trusted`, иначе `Deny`. Allowlist получателей, тип данных и `Readers`/data ACL библиотека не реализует — это ответственность приложения. `Target` у `Send` должен связывать получателя, а не только имя инструмента. Allowlist URL/доменов и удаление внешних markdown-images — полезные дополнительные меры, но не защита от всех текстовых каналов эксфильтрации.

Для RAG и поиска фильтрация прав выполняется приложением до построения контекста. Библиотека не реализует `Readers`/data ACL и не сохраняет reader restrictions после retrieval: если приложение передало документ в `Task`, оно отвечает за то, кому этот документ можно показать.

## 8. Workflow и foreign approval

Workflow рассчитан на типовые use-cases с последовательными шагами, ветвлениями и подтверждением из доверенного источника вне модели — человеком или бизнес-логикой, а не произвольным durable execution engine. В первой версии не поддерживаются параллельные ветви, циклы и динамически генерируемые шаги.

### 8.1. Модель

```go
wf, err := flow.FromEngine[RefundCase](engine, "refund",
    flow.Version(1),
    flow.WithAuthorizer(authz),
    flow.WithAudit(auditSink),
)
if err != nil {
    return err
}
wf.Step("prepare", prepareRefund).
    Approve("manager", flow.ApproveConfig[RefundCase]{
        When:       refundRequiresApproval,
        Permission: "refund:approve",
        FourEyes:   true,
        TTL:        24 * time.Hour,
        Card:       refundApprovalCard,
        Target:     refundResource,
    }).
    Step("execute", executeRefund).
    Step("notify", notifyCustomer)
```

Состояние workflow `S` должно быть явно сериализуемым и ограниченным по размеру. Пользовательский код не должен хранить в нём открытые секреты без необходимости.

`flow.FromEngine` берёт authorizer, audit sink, claim store, часы и ключ подписи у `Engine` (`Engine.Deps`). Два разных authorizer в одном use-case означали бы, что Gate проверяет вызывающего по одному ACL, а одобрение — по другому. `flow.New` остаётся для flow без Task вокруг него.

### 8.2. Состояния

`Running → Suspended → Running → Done` — обычный путь. Дополнительные конечные состояния: `Rejected`, `Expired`, `Failed`. Компенсации (`Compensating`) и `Cancelled` в текущей реализации отсутствуют.

`Start` / `Resume` возвращают явный результат:

```go
type Status uint8
const (
    Running Status = iota
    Suspended
    Done
    Rejected
    Expired
    Failed
)

type Result[S any] struct {
    Status     Status
    State      S
    Suspension *Suspension // nonce, approval card, expiry, requester
}
```

`Status` — явное состояние, а не отсутствие ошибки: `Running` (zero, незавершённый), `Suspended`, `Done`, `Rejected`, `Expired`, `Failed`. Ошибка шага дополнительно ставит `Failed`, поэтому результат и ошибка не расходятся.

Ошибка возвращается вторым значением, а не полем `Result`: два канала для одного факта заставляли бы вызывающего проверять оба.

HTTP-ответ `202 Accepted` может содержать approval card и id сохранённой приостановки, но ни карточка, ни id не являются самим одобрением.

### 8.3. Как приостанавливать Task

Go не умеет безопасно сериализовать стек произвольной функции. Поэтому `gobellim` не обещает магически продолжить выполнение с середины произвольной Go-функции.

Вместо этого `Task` возвращает явный typed outcome: `Completed`, `ApprovalRequired` или `Failed`. При `ApprovalRequired` runtime возвращает `PendingAction` — сериализуемое описание ровно того действия, которое было остановлено: задача, tool, уже разрезолвленные аргументы, digest, tenant, expiry, карточку и HMAC-подпись engine. Tool handler не вызывается.

После реального одобрения приложение вызывает `task.ExecuteApproved(ctx, requester, approver, pending)`. Метод проверяет HMAC, которым engine подписал выданный `PendingAction` (поэтому объект, собранный клиентом или другим процессом без общего `WithApprovalKey`, — `ErrApprovalDrift`), заново прогоняет tenant binding, RBAC/ACL и `Tool.Validate`, сверяет tool/access и digest аргументов с карточкой, фиксирует `approval.granted` с id апрувера и только потом вызывает handler. Потолок access — единственная проверка, которую заменяет решение апрувера. Повторный `ExecuteApproved` с тем же `PendingAction` возвращает `ErrApprovalReplay`.

Это отдельный путь от `flow`. `flow` одобряет шаг workflow, а `Task` — конкретный tool call модели; смешивать их в одном действии не нужно, иначе у одного эффекта окажется два nonce и два TTL. Выбирайте один approval engine на путь.

Уже завершённые шаги не перевычисляются: `flow` продолжает с шага после `Approve`, а `flow.ApproverFrom(ctx)` отдаёт апрувера этому шагу. `Task` не восстанавливает стек и не продолжает модельный цикл после одобрения — новый ход начинается новым `Run`.

### 8.4. Approval card

Карточка — типизированная структура, а UI принадлежит сервису. `PendingAction.Card` содержит те же поля и привязан к digest аргументов:

```json
{
  "run_id": "r_123",
  "flow": "refund",
  "step": "execute",
  "action": { "tool": "orders.refund", "access": "write" },
  "args": { "order_id": "A-1042", "cents": 4900 },
  "reason": "order_id получен из untrusted ticket body",
  "provenance": [
    { "arg": "order_id", "source": "ticket.body", "integrity": "untrusted" }
  ],
  "required_permission": "refund:approve",
  "four_eyes": true,
  "expires_at": "2026-10-24T12:00:00Z"
}
```

Карточка должна объяснять, почему действие остановлено, откуда взялись аргументы, какие ограничения сработали и что именно апрувер разрешает. В текущей реализации `ApprovalCard.Args` содержит уже резолвнутые значения; библиотека не знает личность апрувера в момент приостановки, поэтому сервис обязан применить свой approver ACL перед показом карточки. Сам по себе hash аргументов не доказывает их безопасность; provenance нужен для осмысленного решения.

Поддерживаемые решения: `Approve`, `Reject`. `Reject` необратим: он тоже забирает nonce из `Store`, поэтому ту же приостановку нельзя позже возобновить как `Approve`; повторное решение требует нового `Run`. `DecisionUnknown` и любое неизвестное решение — `ErrDecision`, а не отказ и не одобрение. `Edit` аргументов — P2 и в текущей реализации отсутствует.

### 8.5. Сохранённая приостановка

При паузе `Run` возвращает `Suspension{Nonce, Card, ExpiresAt, Requester}` и сериализованное состояние. Приложение хранит оба значения на сервере и отдаёт клиенту только непрозрачный id. Никакого bearer-токена с зашифрованным состоянием нет, поэтому и ключа шифрования не нужно: единственное доверие здесь — к ключам аутентификации пользователей и к хранилищу приложения.

Это важно и для безопасности, и для поддержки: серверный объект нельзя подменить на клиенте, он не уезжает в браузер и не требует ротации ключей. Цена — таблица приостановок у приложения; для одной реплики хватает process-local `MemStore` для nonce, а для нескольких — общий `Store`.

Размер состояния и TTL ограничиваются приложением — библиотека не сериализует состояние сама и не обещает бесконечного роста. Приостановка отклоняется, если `Card.Flow`, `Card.Step` или `Nonce` не те, с которыми вызывается `Resume`, или если срок истёк.

### 8.6. Resume: обязательные проверки

1. Аутентифицировать approver средствами сервиса и загрузить сохранённую приостановку по id.
2. Проверить tenant approver'а, expiry и `Card.Flow`.
3. Проверить, что `Card.Step` — реальная граница одобрения этого flow.
4. Сверить `RequiredPermission` и `FourEyes` в карточке с текущей конфигурацией: смена approval-политики даёт `ErrFlowDrift`, а не старую политику.
5. Проверить право `Permission` у approver'а, применяя его к цели; `Target.TenantID` должен совпадать с tenant requester'а.
6. Применить Four-Eyes.
7. Перепроверить `ActionPermission` у requester'а **по текущим правилам**, а не по снимку.
8. Пересобрать карточку из состояния и сравнить `ActionDigest`.
9. Атомарно занять nonce в `Store`; после этого продолжить с шага после `Approve`.

Пункты 1–8 выполняет `flow.Resume`; шаг после `Approve` — обычный код приложения, который запускается только после этих проверок. Отдельный путь — `Task.ExecuteApproved`: он исполняет tool call модели и повторяет tenant/authz/`Validate` и сверку digest. `id` шага в карточке сверяется с текущим шагом flow, а не только его индекс. `DecisionUnknown` отклоняется: нулевое значение не является одобрением. `ctx.Err()` проверяется до `Claim`: отменённый запрос не сжигает одобрение.

Если политика теперь запрещает действие, одобрение не переопределяет её: `ExecuteApproved` вернёт `ErrApprovalInvalid`, а workflow перейдёт в отказ.

### 8.7. Store и фактические гарантии

Хранилище опционально; без него `flow` использует process-local `MemStore` — атомарный в процессе и ограниченный по размеру, чтобы удобный дефолт не превращался в утечку памяти.

| Режим         | Где состояние                                            | Реальная гарантия                                                                                                                                                        |
| ------------- | -------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| L0 / MemStore | Suspension и state хранит приложение; nonce — в процессе | Лёгкая интеграция и resume внутри одного процесса. Второй resume в том же процессе отклоняется; между репликами одноразовость не гарантируется.                          |
| L1 / Store    | Suspension и state в БД приложения + таблица claims      | Атомарный claim nonce между репликами, TTL и ограничение повторного resume.                                                                                              |
| L2 / journal  | L1 + устойчивый журнал checkpoint/step results           | Восстановление согласованных шагов после crash до оговорённой границы; требует чётких idempotency контрактов. Не является заменой полноценному durable execution engine. |

`Store` предоставляет атомарный `Claim` nonce. SQL-адаптер принимает `*sql.DB`, подключённый сервисом; библиотека не поднимает БД и не привозит драйвер. Дубликат nonce — это `(false, nil)`, а не ошибка БД; для MySQL есть `ConflictClause`. Просроченные nonce удаляются через `Prune`. При недоступности Store операция `Resume` завершается fail-closed.

Схема таблицы claims — миграция приложения, а не библиотеки: адаптер не создаёт таблиц. DDL с индексом по `expires_at` (иначе `Prune` сканирует таблицу) задокументирован в самом пакете `store/sql`.

**Exactly-once для внешнего эффекта не обещаем.** После отправки запроса во внешний API и падения процесса библиотека может не знать, применился ли эффект. Реалистичная семантика — at-least-once + idempotency key, поддерживаемый системой-получателем, либо транзакционный механизм на стороне приложения.

### 8.8. Compensation

Компенсации — необязательная возможность линейного workflow. При `Reject`, `Cancel`, `Expired` или ошибке запускаются обратные операции для завершённых шагов, если это безопасно и настроено. Компенсация должна быть идемпотентной; сбой компенсации фиксируется как `Failed` и передаётся приложению для ручного разбора. Компенсация — не математический rollback и не всегда может отменить внешний эффект.

### 8.9. Audit и dry-run в процессе внедрения

Режимы разделяются явно:

- **Enforce** — Gate принимает реальные решения и исполняет только разрешённые действия. Это production-защита.
- **DryRun** — workflow и решения проигрываются на тестовых входах, а все инструменты заменены заглушками/симуляторами; внешние эффекты невозможны.
- **ShadowPolicy** — новая policy вычисляется и сравнивается с действующей, но shadow-решение не получает право менять execution path. Это только измерение миграции; если старый путь не имеет собственных защит, shadow-режим сам по себе не обеспечивает prompt-injection protection.

Не вводить режим, в котором Gate логирует `would_deny`, а затем автоматически исполняет запрещённую выплату, отправку или удаление. Если legacy behavior сознательно оставлен на время миграции, это явное решение хозяина сервиса и не должно называться защищённым режимом библиотеки.

В текущей реализации есть только `Enforce`. `DryRun` достигается подменой tool handlers в тестовой сборке (см. `testkit`), а не отдельным режимом runtime. `ShadowPolicy` — P2.

### 9.1. Сигнальный каскад

| ------- | ---------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| 0       | Лимиты размера, числа tool calls, глубины/длины контекста, timeout                       | Обязательные детерминированные ограничения.                                                                    |
| 1       | Базовая нормализация для анализа, поиск контрольных символов/подозрительных разделителей | Сигналы и телеметрия; исходник сохраняется отдельно, если это нужно продукту.                                  |
| 2       | Regex/валидаторы PII и секретов (карточные номера, e-mail, токены и т.п.)                | Маскирование/label, если правило совпало. Нельзя считать regex полным DLP.                                     |
| 3       | Опциональный `Classifier`                                                                | Сигнал риска; deadline и политика поведения при timeout должны быть явными. Не является единственным барьером. |
| 4       | Опциональная модель-судья                                                                | Выключена по умолчанию; не авторизует действия и не отменяет Gate.                                             |

```go
type Classifier interface {
    Classify(ctx context.Context, input ClassificationInput) (Signal, error)
}
```

Ошибка/timeout детектора возвращает `Unknown`, не `Safe`. При этом архитектурная корректность не должна зависеть от успешного ответа классификатора: Gate всё равно валидирует инструмент и права. Для высокорисковых сценариев `Unknown` может усиливать решение до `Escalate`/`Deny`.

### 9.2. Unicode

Нельзя заявлять полноценную NFKC-нормализацию через самописную неполную таблицу. Если полная нормализация нужна, использовать отдельный адаптер с проверенной библиотекой, например `golang.org/x/text`, не включая зависимость в core. Нормализация для детектирования не должна незаметно менять исходные данные, на которых основывается бизнес-решение.

### 9.3. Бюджеты

Обязательны настройки `MaxInputBytes`, `MaxOutputBytes`, `MaxArgBytes`, `MaxContextBytes`, `MaxToolCalls`, `MaxWallTime`, `MaxModelCalls` и `MaxContextItems`. `MaxContextItems` считает сообщения и при дефолтах почти недостижим; реальный объём ограничивает `MaxContextBytes` — сумма текста сообщений и аргументов tool calls. Бюджеты можно уточнить на задачу через `TaskConfig.Limits`; нулевое поле наследует значение `Engine`. Числа по умолчанию фиксируются после бенчмарков и eval; настраиваемые бюджеты передаются в runtime, а не только указываются модели в prompt.

### 9.4. Выходная безопасность

Выход проходит schema/size validation, правила раскрытия чувствительных данных и безопасное представление. HTML/Markdown рендерится приложением в собственном безопасном режиме. Санитайзер URL или удаление внешних картинок могут помочь, но не заменяют контроля доступа к данным, переданным модели, и политики `Send`.

## 10. Наблюдаемость и аудит

Core публикует события через `slog` и интерфейс `AuditSink`. По умолчанию не логируются полные промпты, сырые ответы, PII, secret values и approval nonces.

`AuditSink` обязателен: `New` и `flow.New` без `WithAudit` возвращают `ErrInvalidConfig`. Запуск без audit-следа — это решение, которое принимается явно (`SlogSink` с `slog.DiscardHandler`), а не забытая опция.

Минимальные поля события:

- `run_id`, `task`/`flow`, `step`, `request_id`;
- анонимизированный или внутренний `principal_id`, tenant reference;
- tool name, access, decision, rule IDs, policy version;
- digest canonical arguments, source labels, latency, model/tool call counts;
- model name, prompt/completion/total tokens для `model.completed`;
- suspension/approval state, nonce reference, error class.

Предлагаемые типы событий: `task.started`, `task.completed`, `task.suspended`, `task.failed`, `model.completed`, `gate.allowed`, `gate.denied`, `gate.escalated`, `tool.completed`, `workflow.suspended`, `approval.requested`, `approval.granted`, `approval.denied`, `workflow.resumed`, `workflow.expired`, `policy.drift`, `workflow.failed`.

Append-only JSONL и hash chain можно реализовать как адаптер. Hash chain сам по себе не гарантирует неизменность, если злоумышленник может переписать весь файл и все хеши; для tamper-evidence нужна внешняя фиксация/выгрузка контрольного значения. OTel — отдельный пакет, а не обязательная зависимость.

## 11. Тестирование и replay

### 11.1. Security invariant suite

`testkit` должен поддерживать scripted `FakeModel`, которая намеренно предлагает запрещённые tool calls, выдуманные handles, чужие tenant IDs, большие аргументы и недопустимые enum values. Тесты должны проверять свойства системы, а не надеяться, что реальная модель всегда будет вести себя корректно.

Пример целевого теста (API условный):

```go
func TestUntrustedInputCannotExecuteWriteWithoutGate(t *testing.T) {
    h := testkit.New(t, refundTask,
        testkit.MaliciousModel(testkit.TryAllTools()),
    )

    got := h.Run(poisonedTicket)
    require.NotExecuted(t, got, "orders.refund")
    require.Decision(t, got, gobellim.Escalate, "orders.refund")
}
```

Этот тест и corpus не являются формальным доказательством безопасности. Они нужны для автоматического предотвращения известных классов регрессий и должны дополняться threat modeling, code review и, для высоких рисков, независимым security review.

### 11.2. Обязательные категории тестов

- direct и indirect prompt injection, документы с поддельными role tags, Unicode/control characters;
- межтенантный доступ, изменение object ID, ACL до retrieval и перед tool execution;
- невалидная схема, неизвестный инструмент, превышенные бюджеты, ошибка авторизации;
- egress/PII/secret handling, попытки раскрыть поля, не доступные readers;
- tampered/expired/other-tenant suspensions, wrong flow version, replay и параллельный Resume;
- изменённые аргументы после approval, отозванные права, Four-Eyes/quorum, TTL;
- сбой процесса между внешним эффектом и commit, повтор с idempotency key, сбои компенсации;
- отказ/timeout classifier и Store;
- fuzzing JSON decode, tag schema, grounding и canonicalization.

### 11.3. Replay и policy diff

Бизнес-проверки и `Decide` должны быть отделены от транспорта настолько, насколько это возможно. Для сохранённых трасс создаётся минимизированное представление: labels, access, решение, rule IDs, schema outcome и стабильные хеши вместо секретных значений. `replay.Diff(old, new, traces)` показывает переходы `Allow → Escalate`, `Allow → Deny` и обратные изменения, а также прогноз числа approval requests.

Не отправлять неотредактированный production-трафик с PII в общие replay-окружения автоматически. Состав корпуса, срок хранения и возможность восстановления исходных значений — отдельное решение владельца данных.

### 11.4. Метрики качества

- доля запрещённых действий, которые всё же исполнены на attack corpus — целевой показатель 0;
- false escalation / approval requests на 100 легитимных кейсов;
- доля корректно решённых легитимных задач;
- p50/p95/p99 накладной latency core отдельно от сетевого вызова модели;
- model/tool calls на запрос, токены/стоимость, число ошибок по классам;
- расхождения decision при обновлении policy/model/prompt.

## 13. Ограничения и гарантии

### Гарантируемые свойства при корректной интеграции

- Ответ модели не является достаточным основанием для исполнения: все модельные tool calls проходят через Gate.
- Неизвестный инструмент, ошибка schema validation, ошибка авторизации и несовпадение `Resource.TenantID` с `Principal.Tenant` не приводят к `Allow`.
- `ground`-аргумент нельзя удовлетворить сырой строкой от модели: нужен существующий handle, созданный для этого запуска.
- Библиотека не управляет retrieval: если приложение передаёт документы в `Task`, оно само применяет data ACL до сборки контекста.
- Свободный вывод модели не становится trusted только за счёт JSON schema или перефразирования.
- Approval относится к конкретному действию и аргументам; после их изменения policy и validation запускаются снова.
- `Task.ExecuteApproved` повторно проверяет tenant, RBAC/ACL, `Tool.Validate` и digest; потолок access — единственное, что заменяет одобрение апрувера.
- `sensitivity`-теги на результате инструмента не дают секрету вернуться в контекст модели; лучший-effort: map и self-marshalling типы не инспектируются.
- Завершившийся без явного outcome `Run` (включая панику handler'а) аудируется как `task.failed`, а не `task.completed`.
- В режиме `Enforce` действие, принятое Gate как `Deny` или `Escalate`, не выполняется без установленного процесса одобрения.

Эти гарантии зависят от того, что разработчик не обходит библиотеку прямым вызовом бизнес-функций и корректно размечает источники/access инструментов. `gobellim` — библиотека внутри доверенного процесса, а не sandbox против злонамеренного Go-кода того же процесса.

### Не гарантируем

1. Полное предотвращение генерации вредоносного или ложного текста.
2. Точное восстановление внутренних зависимостей свободного текста от отдельных элементов контекста.
3. Защиту от side-channel, timing и всех каналов утечки.
4. Exactly-once внешний side effect без поддержки со стороны вызываемой системы.
5. Межрепличную одноразовость Resume в L0 без общего атомарного Store.
6. Одноразовость `Task.ExecuteApproved` между репликами без общего `ClaimStore`: процессный claim по умолчанию защищает только внутри процесса.
7. Durable recovery любого непрерывного участка исполнения Go-функции.
8. Корректность бизнес-политик, если приложение ошибочно описало permissions, directories или tool access.
9. Эффективность конкретного классификатора вне измеренного eval corpus.

## 14. Roadmap и критерии приёмки

### MVP / хакатон

| Приоритет | Что входит                                                                                                                | Критерий приёмки                                                                                                             |
| --------- | ------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| P0        | `Task[In,Out]`, `Model`, типизированные tools, schema validation, Gate, `Authorizer`, access policy, limits, audit events | Один сценарий запускается в существующем сервисе без отдельной инфраструктуры; запрещённый tool call не исполняется.         |
| P0        | Labels и handles для выбранных чувствительных полей, базовый provenance                                                   | У свободного ответа модели нет автоматического trust promotion; несуществующий handle отклоняется.                           |
| P0        | `FakeModel`, malicious testkit, ≥30 целевых сценариев                                                                     | CI покрывает невалидные аргументы, RBAC/ACL, untrusted-to-write, send и лимиты.                                              |
| P1        | Линейный workflow, approval card, сохранённая приостановка, expiry/version check, policy re-check                         | Resume отвергает expired/other-tenant/changed-policy приостановку; approval не выполняет операцию при отозванном permission. |
| P1        | SQL `Store` L1 поверх `database/sql`                                                                                      | Параллельный Resume использует атомарный claim; replay на другой реплике отклоняется.                                        |
| P2        | Replay/diff, policy migrations, Four-Eyes/quorum, compensation                                                            | Regression suite показывает decision diff и тестирует отказ при policy drift.                                                |
| P2        | Model/HTTP adapters, OTel                                                                                                 | Подключаются отдельно и не попадают в обязательные зависимости core.                                                         |

P0 и P1 реализованы, кроме sealed continuation: токена нет, `Suspension` и `State` хранит приложение (§8.5). В `flow` также реализован Four-Eyes. Реализованы `plugins/gigachat` (model adapter) и `plugins/langfuse` (audit sink). P2 (sealed continuation, replay/diff, policy migrations, quorum, compensation, `detect`, `httpapproval`, `otel`, `Edit` аргументов) — нет.

### Демо

1. Микросервис получает тикет с обычным запросом и с отравленной инструкцией внутри текста.
2. LLM предлагает классификацию и потенциальный возврат.
3. Gate показывает, как отличаются `Allow`, `Deny` и `Escalate`; опасное действие не исполняется без валидного разрешения.
4. Approval card раскрывает provenance и причину эскалации с маскированием данных.
5. Изменение args/ACL после одобрения приводит к повторной проверке и блокировке, если политика больше не разрешает действие.
6. CI прогоняет malicious corpus; replay diff сравнивает две версии policy.

### Базовые цели производительности — проверить, не рекламировать

- core без сети/LLM/классификатора: p95 накладной стоимости `Gate` стремится быть менее 1 ms на типичном инструменте;
- ноль обязательных внешних сервисов;
- лимиты и отказоустойчивость не зависят от модели;
- бюджет классификатора конфигурируется и измеряется отдельно;
- любая метрика latency публикуется только после benchmark на зафиксированной версии Go, железе и корпусе.

## 15. Открытые вопросы

1. Нужен ли `flow.Checkpoint()` в v0.1 или достаточно явного результата `ApprovalRequired` и ограничения «один suspending Task на шаг»?
2. Какие аргументы должны быть обязательными handles в первой версии, а какие можно передавать raw с консервативными labels?
3. Нужен ли встроенный JSON Schema subset с поддержкой nested structs, либо лучше начать с простой схемы и явных Go validators?
4. Какую минимальную SQL-схему поддерживать в `Store.SQL`, не навязывая диалект конкретной БД?
5. Какие дефолтные лимиты размеров, tool calls, TTL приостановки выбирать после нагрузочных и attack-тестов?
6. Какие изменения policy должны требовать немедленного отказа, а какие допускают явную миграцию старого workflow state?
7. Как проверять не только unauthorized actions, но и сохранение полезности легитимных сценариев без зависимости от случайности провайдера?
8. Резолвить ли handles в `Out` или только вычищать неизвестные `<hN>`? Сейчас не делается ни то ни другое, поэтому хэндл может попасть в ответ пользователю.

## 16. Источники и prior art

- **CaMeL — Defeating Prompt Injections by Design:** https://arxiv.org/abs/2503.18813 — контроль потока, происхождение данных и capabilities. Используем эти принципы, но сохраняем фиксированный workflow Go вместо универсального interpreter/agent runtime.
- **NVIDIA NeMo Guardrails:** https://github.com/NVIDIA-NeMo/Guardrails и https://docs.nvidia.com/nemo/guardrails/configure-guardrails/yaml-schema/guardrails-configuration — полезное разделение проверок на input, retrieval, execution и output rails. `gobellim` не копирует большой конфигурационный DSL; основная граница безопасности находится в Gate.
- **cloud-ru-tech/guardrails-llm-filter:** https://github.com/cloud-ru-tech/guardrails-llm-filter — референс для обособленного masking/PII-компонента, не достаточная самостоятельная защита от prompt injection.
- **GLiNER Guard:** https://arxiv.org/html/2605.05277v1 — кандидат для необязательного классификатора/детектора; сначала измерить precision/recall и latency на своих корпусах.
- **Stripe, Scaling up your microservice testing with Apache Spark:** https://stripe.dev/blog/microservice-testing-with-apache-spark — отделение детерминированной бизнес-логики от request path и replay исторического распределения inputs для измерения регрессий.
- **OWASP GenAI Security Project, Top 10 for LLM Applications 2026:** https://genai.owasp.org/initiatives/top-10-for-llm-and-genai/ — актуальные классы рисков, включая prompt injection, sensitive information disclosure, excessive agency и unbounded consumption.
- **Positive Technologies, «Не словом, а кодом: как организовать защиту LLM без потерь производительности»:** https://ptsecurity.com/research/webinar/ne-slovom-a-kodom-kak-organizovat-zashchitu-llm-bez-poter-proizvoditelnosti/ — дополнительный практический материал; конкретные утверждения из вебинара не используются без проверки содержимого.

### Позиционирование

Дифференциация `gobellim` — в сочетании лёгкой интеграции для существующего Go-сервиса, закрытого execution Gate, консервативных labels/provenance, встроенного контракта foreign approval и replay-ориентированного тестирования. Это инженерное объединение известных идей, а не заявление о фундаментальной новизне.
